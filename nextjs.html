Introduction

Next.js is a full-stack React framework. React by itself only renders UI in the browser; Next.js adds the missing production pieces — a router, server rendering, data fetching, caching, bundling, an API layer, and deployment conventions — so you can build a complete app, not just a component tree.

What it is

Next.js is built and maintained by Vercel. It runs your React components on a Node.js (or edge) server as well as in the browser, and it ships an opinionated project layout where the file system is your router. The current, recommended model is the App Router (the app/ directory, stable since Next 13.4); the older Pages Router (pages/) still works but new projects should use the App Router — this guide focuses on it.

Why it exists — the problem it solves

A plain React app (e.g. Create-React-App / Vite SPA) has real gaps in production:

Plain React SPA problemHow Next.js solves it
Blank HTML until JS loads → bad SEO & slow first paintServer-renders HTML so crawlers & users see content immediately
No routing built in (add React Router)File-system routing built in
All code shipped to the browser (big bundles)Server Components keep data/logic on the server — zero JS for them
You wire up your own bundler, code-splitting, image optimizationBuilt-in bundling, automatic code-splitting, <Image>, <font>
Need a separate backend for APIsRoute Handlers & Server Actions run backend code in the same project
No caching strategyA multi-layer caching system with revalidation

Mental model

Request ─▶ Next.js server (Node / Edge) │ ├─ match URL to a file in app/ (routing) ├─ run Server Components on server (fetch data, no JS shipped) ├─ render HTML ───────────────▶ browser shows content instantly (fast FCP, SEO) └─ send minimal JS for Client Components │ hydration makes it interactive
One-line definition: Next.js = React + a server + a router + a data/caching layer + a build system, wrapped in file-based conventions so you ship a fast, SEO-friendly, full-stack app with far less boilerplate.

✅ Key takeaways

  • Next.js is a full-stack React framework: server rendering, routing, data/caching, and an API layer in one project.
  • It solves SPA weaknesses: SEO, first-paint speed, bundle size, and backend wiring.
  • Use the App Router (app/) for new projects; create-next-app scaffolds it.
What is Next.js and why use it over plain React?

Next.js is a React framework that adds server-side rendering, file-based routing, Server Components, a caching layer, and an API layer. Over a plain React SPA it gives you SEO-friendly server-rendered HTML, faster first paint, smaller client bundles, and full-stack capability without stitching together many libraries.

Why Next.js (vs the alternatives)

Choosing a framework is a design decision. Here's when Next.js is the right call and when it isn't.

OptionBest forTrade-off
Next.jsSEO-critical apps, full-stack apps, content + dashboards, teams wanting one frameworkOpinionated; server infra to run (or use Vercel)
Vite + React SPAInternal tools, dashboards behind login (SEO irrelevant)No SSR/SEO, no built-in backend
RemixWeb-standards-first, nested data loadingSmaller ecosystem
AstroMostly-static content sites, minimal JSLess suited to highly interactive apps
Plain Node/Express + ReactFull controlYou build everything Next gives free

Advantages

  • Performance by default — server rendering, automatic code splitting, image/font optimization, streaming.
  • SEO — real HTML for crawlers, first-class Metadata API.
  • Full-stack — Route Handlers + Server Actions remove the need for a separate API for many apps.
  • DX — file-based routing, fast refresh, TypeScript, conventions reduce decisions.

Disadvantages / when to avoid

  • You need a Node/edge runtime to serve it (a purely static host works only for fully static output).
  • The caching model is powerful but has a learning curve (covered in depth later).
  • For a small internal SPA with no SEO needs, Vite may be simpler.
Interview framing: "Next.js trades some flexibility for production-ready defaults (rendering, routing, caching, images). Choose it when SEO/performance/full-stack matter; choose a Vite SPA when you only need a client-rendered app behind auth."

Version evolution (why the framework changed)

Pages Router (getServerSideProps / getStaticProps, client-first) ↓ React 18 (Suspense, streaming SSR, concurrent features) App Router (React Server Components, nested layouts, caching) ↓ React 19 (async components, use(), Server Actions, useOptimistic) Today (App Router + PPR + Turbopack)

Understanding this arc explains the API: the App Router exists because React 18/19 added the primitives (streaming, RSC, Actions) that make server-first rendering practical. Migrating from Pages → App is incremental (they coexist in one app).

✅ Key takeaways

  • Pick Next.js for SEO/performance/full-stack; pick a SPA for simple internal tools.
  • Its superpower is production-ready defaults; its cost is opinionation + a server to run it.

Project Structure

Everything routable lives under app/. Folders become URL segments; special files give each segment behavior.

my-app/ ├─ app/ # the App Router (routes live here) │ ├─ layout.tsx # ROOT layout (required) — wraps every page, has <html><body> │ ├─ page.tsx # the "/" route │ ├─ globals.css │ ├─ loading.tsx # loading UI for "/" │ ├─ error.tsx # error UI (Client Component) │ ├─ not-found.tsx │ ├─ dashboard/ │ │ ├─ page.tsx # "/dashboard" │ │ └─ settings/page.tsx # "/dashboard/settings" │ └─ api/ │ └─ users/route.ts # "/api/users" (Route Handler) ├─ components/ # shared React components (not routes) ├─ lib/ # data access, helpers (server-only code) ├─ public/ # static assets served at "/" ├─ next.config.js ├─ middleware.ts # runs before requests (edge) └─ tsconfig.json
FolderPurpose
app/Routes + route-scoped UI (layouts, loading, error).
public/Static files (images, robots.txt) served from the root URL.
components/, lib/Non-routable code you import. Convention, not enforced.

Common mistake: putting a page.tsx in a folder you only meant as a helper — any folder with page becomes a public URL. Keep non-route code out of app/ (or in a _folder which is private).

App Router (the core model)

The App Router is the routing + rendering engine built on React Server Components. Understanding it is 80% of understanding Next.js.

App Router vs Pages Router

✅ App Router (app/)

  • Server Components by default (less JS)
  • Nested layouts, streaming, Suspense
  • fetch-based data + caching
  • Server Actions, PPR — the future

Pages Router (pages/)

  • Traditional React model (no Server Components)
  • getServerSideProps/getStaticProps
  • Simpler, mature, still supported
  • No new features being added

How a request flows

URL "/dashboard/settings" │ ▼ match nested segments app/layout.tsx ──▶ app/dashboard/layout.tsx ──▶ app/dashboard/settings/page.tsx (root shell) (dashboard shell) (the page) │ ▼ Server Components render on the server → HTML streamed to the browser ▼ Client Components hydrate for interactivity

✅ Key takeaways

  • The App Router nests layouts down the URL and renders on the server by default.
  • Prefer it for new apps; the Pages Router is legacy-but-supported.

File Conventions

Special filenames inside a route folder give it behavior. Memorize these — they are the vocabulary of the App Router.

FileRole

layout.tsxShared shell that wraps a segment + its children; preserves state across navigation, doesn't re-render.
template.tsxLike layout but re-creates a new instance on each navigation (resets state/effects).
loading.tsxInstant loading UI (wraps the segment in a Suspense boundary).
error.tsxError boundary for the segment (must be a Client Component).
not-found.tsxRendered by notFound() or unmatched routes.
route.tsAn API endpoint (Route Handler) instead of a page.
[id], [...slug], [[...slug]]Dynamic, catch-all, optional-catch-all segments.
(group)Route group — organizes files without adding a URL segment.

Design tip: a folder with only a layout.tsx and no page.tsx is not itself reachable — it just wraps its children. That's how you add a shell (e.g. a dashboard sidebar) to a group of routes.

Routing

Folders map to URL paths; a page.tsx makes a path public. There is no route config file — the file tree is the config.

app/dashboard/page.tsx → /dashboard
export default function DashboardPage() {
  return <h1>Dashboard</h1>;
}

Route groups & private folders

Organize without changing URLs
app/
  (marketing)/       # group: NOT in the URL
    about/page.tsx    # → /about   (not /marketing/about)
    layout.tsx        # a marketing-only shell
  (app)/

Why groups matter: you can give the marketing pages one layout and the app pages a different layout, while keeping clean URLs — a real-world pattern for public site + logged-in app in one project.

✅ Key takeaways

  • Folder = URL segment; page.tsx = public page.
  • (group) organizes routes and lets you scope layouts without affecting the URL.

Dynamic Routes & Params

Square-bracket folders capture URL segments. In the App Router, params and searchParams are async (await them).

app/blog/[slug]/page.tsx → /blog/hello
export default async function Post({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;          // e.g. "hello"
  const post = await getPost(slug);
  return <article>{post.title}</article>;
}
PatternMatchesparams
[slug]/blog/hello{ slug: "hello" }
[...slug]/docs/a/b/c{ slug: ["a","b","c"] }
[[...slug]]/docs and /docs/a/boptional (may be undefined)

Pre-generating dynamic pages

generateStaticParams — build a static page per slug (SSG)
export async function generateStaticParams() {
  const posts = await getAllPosts();
  return posts.map((p) => ({ slug: p.slug })); // each becomes a static route at build
}
Common mistake: forgetting to await params in Next 15 — params/searchParams are Promises now. Destructuring them synchronously throws.
Why are they Promises? Making params/searchParams async lets Next start rendering the static parts of the page before these dynamic values resolve — it fits React's async rendering model and the use() API, and keeps a page from being forced fully-dynamic just to read a param.

Layouts & Templates

Layouts are persistent shells shared by a segment and its children. The root layout is required and must render <html> and <body>.

app/layout.tsx (root)
export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>
        <Nav />
        {children}          /* the active page renders here */
      </body>
    </html>
  );
}

Layout vs Template

layout.tsxtemplate.tsx
State across navigationPreserved (not remounted)Reset (new instance each nav)
Effects re-run on navNoYes
Use forPersistent nav, sidebarsPer-page enter animations, resetting logs
Nesting: layouts compose down the tree. app/layout wraps everything; app/dashboard/layout wraps only /dashboard/*. Navigating within a shared layout only re-renders the changing part — this is why the App Router feels instant.

✅ Key takeaways

  • Root layout is required and owns <html>/<body>.
  • Layouts persist (keep state); templates remount (reset state).

Loading, Error & Not-Found UI

Drop a special file into any segment to get built-in loading skeletons and error boundaries — no manual Suspense/try-catch wiring.

loading.tsx — shown instantly while the page's data loads
export default function Loading() {
  return <div className="skeleton">Loading…</div>;   /* Next wraps page in <Suspense fallback={this}> */
}
error.tsx — must be a Client Component
"use client";
export default function Error({ error, reset }: { error: Error; reset: () => void }) {
  return (
    <div>
      <p>Something went wrong: {error.message}</p>
      <button onClick={reset}>Try again</button>  /* re-render the segment */
    </div>
  );
}
Why error.tsx is a Client Component: error boundaries need React state and event handlers (the reset button), which only exist on the client. It catches errors from the page and its children, not from the layout at the same level (put a higher error.tsx for that, or use global-error.tsx).

Metadata, Fonts & Images

Next.js gives first-class, SEO-friendly primitives for the head tags, web fonts, and images — three things you'd otherwise hand-optimize.

Metadata API (SEO)

Static & dynamic metadata
// static — export a metadata object from a layout or page
export const metadata = { title: "Blog", description: "Latest posts" };

// dynamic — compute per-request (e.g. per blog post)
export async function generateMetadata({ params }) {
  const { slug } = await params;
  const post = await getPost(slug);
  return { title: post.title, openGraph: { images: [post.cover] } };
}

Images & Fonts

next/image & next/font

Server Components (RSC)

In the App Router, components are Server Components by default. They render on the server, can be async, can access the database/filesystem directly, and ship zero JavaScript to the browser.

What / Why / How they work

  • What: a React component that runs only on the server during the request; its output is serialized to the client as RSC payload (not re-executed in the browser).
  • Why: smaller bundles (their code never ships), direct data access (no API round-trip), keep secrets server-side.
  • Internal working: the server renders the RSC tree → produces HTML + a compact "RSC payload" describing the component tree → the browser paints HTML instantly and reconciles; only Client Components hydrate.
An async Server Component fetching data
// app/users/page.tsx — no "use client", so it's a Server Component
import { db } from "@/lib/db";
export default async function Users() {
  const users = await db.user.findMany();   // direct DB access — runs on server only
  return <ul>{users.map((u) => <li key={u.id}>{u.name}</li>)}</ul>;
}
Server Components can't: use hooks (useState/useEffect), use browser APIs, or attach event handlers (onClick). Those require a Client Component.
Best practice: keep components on the server as long as possible; push the "use client" boundary down to the smallest interactive leaf (e.g. a like button), not up at the page. This minimizes shipped JS.
Enforce the boundary: add import "server-only" to modules that must never reach the browser (they use secrets/DB) — the build errors if a Client Component imports them. Use import "client-only" for browser-only modules to catch the reverse mistake.

Client Components

Add "use client" at the top of a file to opt a component (and its imports) into the browser: state, effects, event handlers, browser APIs.

A Client Component
"use client";
import { useState } from "react";
export default function Counter() {
  const [n, setN] = useState(0);
  return <button onClick={() => setN(n + 1)}>{n}</button>;
}

The golden rule: composition

A Server Component can import and render a Client Component. A Client Component can't import a Server Component, but it can receive one as children (or a prop). This "server wraps client, passes server content as children" pattern keeps most of the tree on the server.

Pass a Server Component as children into a Client Component
// ClientShell is "use client"; ServerData is a Server Component
<ClientShell>
  <ServerData />   /* still rendered on the server, just slotted in */
</ClientShell>
Server ComponentClient Component
Default in app/YesNo (opt in with "use client")
Data fetchingDirect (async, DB, fetch)via effects/SWR/React Query or props
Hooks / eventsNoYes
Ships JS to browserNoYes (hydrates)
Access secrets/envYesNo (only NEXT_PUBLIC_*)

✅ Key takeaways

  • Server = default, no JS, data + secrets. Client = interactivity, ships JS.
  • Push "use client" to the leaves; pass server content as children into client wrappers.
Server vs Client Components — when do you use each?

Use Server Components for data fetching, accessing secrets, and static content (they ship no JS). Use Client Components only where you need interactivity — state, effects, event handlers, or browser APIs. Keep the client boundary as small as possible to minimize bundle size, and pass server-rendered content into client components via children.

Rendering: SSR · SSG · ISR · CSR · PPR

"Rendering strategy" = when and where a page's HTML is produced. Next.js supports all of them, chosen per-route by how you fetch data.

StrategyWhen HTML is builtBest forHow to get it
SSG (Static)At build time, onceBlogs, docs, marketing — same for everyoneDefault when no dynamic data / generateStaticParams
ISR (Incremental)Build time, then re-generated on a timer/on-demandContent that changes occasionally (product pages)fetch(url,{next:{revalidate:60}})
SSR (Dynamic)On every requestPersonalized/real-time (dashboards, auth'd data)cache:"no-store" or reading cookies/headers
CSR (Client)In the browser after loadHighly interactive widgets behind authClient Component + client fetch
PPR (Partial Prerender)Static shell instantly + dynamic holes streamedPages mixing static + personalized partsExperimental (available on supported Next.js releases/targets): static page with Suspense'd dynamic parts
Key idea: in the App Router you don't pick a strategy with a special export — you pick it by how you fetch. Cached fetch → static; no-store or dynamic APIs (cookies/headers) → per-request SSR; a revalidate time → ISR. This is the single most-asked Next.js interview concept.
SSG: build ──▶ [HTML on CDN] ──▶ user (fastest, but stale until rebuild) ISR: build ──▶ [HTML on CDN] ──(after N s)──▶ regenerate in background SSR: request ──▶ server renders fresh HTML ──▶ user (always current, slower) CSR: load JS ──▶ browser fetches + renders (no SEO for that data) PPR: static shell now + dynamic parts streamed in (best of both)

✅ Key takeaways

  • Strategy is chosen by data-fetching options, not a mode flag.
  • Static/ISR for shareable content; SSR for per-user/real-time; PPR blends them.
Explain SSR vs SSG vs ISR and how you choose in Next.js.

SSG builds HTML once at build time (fast, cacheable, but static). ISR is SSG plus background regeneration after a revalidate window (fresh-ish without rebuilds). SSR renders on every request (always current, needed for personalized/auth'd data, but higher latency). In the App Router you select these implicitly: a cached fetch → static; revalidate: N → ISR; no-store or using cookies/headers → SSR.

Data Fetching

Fetch data directly in Server Components with async/await. No getServerSideProps, no client loading spinners for initial data.

Fetch in a Server Component + parallelize
export default async function Page() {
  // ❌ sequential (waterfall): each await blocks the next
  // const user = await getUser(); const posts = await getPosts();

  // ✅ parallel: start both, then await together
  const [user, posts] = await Promise.all([getUser(), getPosts()]);
  return <Profile user={user} posts={posts} />;
}
WhereHow to fetch
Server Component (preferred)await fetch(...) or a DB client directly
Client ComponentReact Query / SWR, or call a Route Handler / Server Action
MutationsServer Actions (next section) or POST to a Route Handler
Avoid request waterfalls: independent requests should run with Promise.all. Dependent requests (need result A to fetch B) are unavoidable — isolate them behind a <Suspense> so the rest of the page streams.

Caching & Revalidation

Caching is Next.js's most powerful — and most confusing — feature. There are four caches; know what each does and how to bust it.

CacheWhat it storesInvalidate with
Request MemoizationDuplicate fetches in one renderAutomatic (per request)
Data Cachefetch results across requests/usersrevalidate time, revalidateTag, no-store
Full Route CacheRendered HTML/RSC of static routesRedeploy, revalidatePath
Router Cache (client)Visited routes in the browserrouter.refresh(), time
Control caching per fetch
fetch(url, { cache: "force-cache" });                 // explicitly opt into caching (static)
fetch(url, { next: { revalidate: 60 } });              // ISR: refresh at most every 60s
fetch(url, { cache: "no-store" });                    // SSR: always fresh, never cache
fetch(url, { next: { tags: ["posts"] } });            // tag it for on-demand invalidation
On-demand revalidation (e.g. after a mutation / CMS webhook)
import { revalidateTag, revalidatePath } from "next/cache";
revalidateTag("posts");          // bust every fetch tagged "posts"
revalidatePath("/blog");         // rebuild a specific route's cache
Common mistake: expecting fresh data but a cached fetch silently serves stale results. When data must be live (dashboards, cart), use no-store; when it changes on an event, use tags + revalidateTag.
Next 15 note: defaults shifted toward less aggressive caching (uncached fetch and Route Handlers are dynamic by default). Always be explicit about caching intent rather than relying on defaults.

✅ Key takeaways

  • Four caches: request-memo, data, full-route, router. Learn what busts each.
  • Choose per fetch: force-cache (static), revalidate (ISR), no-store (dynamic), tags (on-demand).

Route Handlers (API endpoints)

A route.ts file is a backend endpoint built on the Web Request/Response APIs — your REST/webhook layer inside the same project.

app/api/users/route.ts → /api/users
import { NextResponse } from "next/server";

export async function GET(req: Request) {
  const users = await db.user.findMany();
  return NextResponse.json(users);
}

export async function POST(req: Request) {
  const body = await req.json();
  const user = await db.user.create({ data: body });
  return NextResponse.json(user, { status: 201 });
}
When to use a Route Handler vs a Server Action: use Route Handlers for public APIs, webhooks, or non-form clients (mobile app, third parties). Use Server Actions for your own app's form mutations (next section) — less boilerplate, progressive enhancement.
Common mistake: naming the file route.ts in a folder that also has page.tsx — a segment can't be both a page and an endpoint. Give the API its own path (usually under app/api/).

Server Actions & Forms

A Server Action is a function marked "use server" that runs on the server but is called directly from your components/forms — no manual API route, no fetch. It's the modern way to do mutations.

A form powered by a Server Action
// app/todos/actions.ts
"use server";
import { revalidatePath } from "next/cache";
export async function addTodo(formData: FormData) {
  const title = formData.get("title") as string;
  await db.todo.create({ data: { title } });
  revalidatePath("/todos");        // refresh the list
}

// app/todos/page.tsx (Server Component) — no client JS needed
<form action={addTodo}>
  <input name="title" /> <button>Add</button>
</form>
  • Progressive enhancement: the form works even before/without JS (it POSTs to the server).
  • Pending/optimistic UI: use useFormStatus and useOptimistic in a client wrapper for instant feedback.
  • Security: validate inputs (Zod) and check auth inside the action — it's a public entry point, treat it like an API route.
Common mistake: trusting Server Action input. Anyone can invoke it; always authenticate and validate server-side.
"use server" placement: put it at the top of a file to make every exported function an action, or inline as the first line inside a function for a single action. Actions must be async and can be imported into Client Components and passed to <form action={...}>.

✅ Key takeaways

  • Server Actions = server mutations callable from components/forms, no API boilerplate.
  • They enable progressive enhancement; still require auth + validation server-side.

Streaming & Suspense

Streaming sends HTML to the browser in chunks as it becomes ready, so a slow data fetch doesn't block the whole page. <Suspense> marks the boundaries.

Stream a slow section while the shell renders instantly
import { Suspense } from "react";
export default function Page() {
  return (
    <>
      <Header />                          /* instant */
      <Suspense fallback={<Skeleton />}>
        <SlowFeed />                       /* streams in when its data resolves */
      </Suspense>
    </>
  );
}
Why it matters: Time-to-First-Byte and First-Contentful-Paint stay low even when part of the page is slow. loading.tsx is just a Suspense boundary around the whole page; explicit <Suspense> lets you stream parts.

Concurrent rendering (what powers streaming)

Streaming rides on React's concurrent renderer. Instead of rendering the whole tree in one blocking pass, React can:

  • Interruptible rendering: pause low-priority work to handle urgent updates (typing, clicks) first.
  • Priorities / Scheduler: urgent updates (input) beat transitions (useTransition) and background streaming.
  • Suspense coordination: a boundary shows its fallback while its subtree's data is pending, then swaps in the resolved content — the server streams these swaps as chunks.
Mental model: Suspense = “wait here, show a fallback”; the concurrent scheduler decides what renders first; streaming is how the server delivers those resolved boundaries over time.

Middleware

middleware.ts runs on the edge, before a request reaches a route — perfect for auth gating, redirects, rewrites, i18n, and headers.

middleware.ts — protect /dashboard
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

export function middleware(req: NextRequest) {
  const token = req.cookies.get("session")?.value;
  if (!token) return NextResponse.redirect(new URL("/login", req.url));
  return NextResponse.next();
}
export const config = { matcher: ["/dashboard/:path*"] }; // only run on these paths
Edge constraints: middleware runs on the Edge runtime — no Node APIs, no heavy DB drivers, keep it fast. Do a cheap check (cookie present, JWT verify); do full auth/data in the route/Server Component.

Parallel & Intercepting Routes

Two advanced patterns that unlock dashboard-style and modal UX.

Cookies & Headers

Read/write cookies and read headers on the server. Note: using these makes a route dynamic (per-request SSR).

cookies() & headers() (async in Next 15)
import { cookies, headers } from "next/headers";
const cookieStore = await cookies();
const session = cookieStore.get("session")?.value;
cookieStore.set("theme", "dark", { httpOnly: true, secure: true, sameSite: "lax" });

const h = await headers();
const ua = h.get("user-agent");
Trade-off: reading cookies/headers opts the route out of static rendering (it must run per request). Only read them where you truly need per-user data.

Authentication & Authorization

Auth in Next.js spans middleware (gate), Server Components (read session), Server Actions/Route Handlers (verify on mutation). A library like Auth.js (NextAuth) or Clerk wires the flow.

Login ──▶ set httpOnly session cookie (server) Request ──▶ middleware: cookie present? no → /login ──▶ Server Component: read session, load user data Mutation ──▶ Server Action: re-verify session + role (never trust the client)
ConcernWhere
Coarse gate (is there a session?)middleware.ts
Load current userServer Component / a getSession() helper
Fine authorization (role/ownership)Inside the Server Action / Route Handler
Session storagehttpOnly, Secure, SameSite cookie (not localStorage)
Golden rule: middleware is a convenience gate, not real security. Middleware should perform only coarse-grained authentication (is there a valid session?); authorization and data-ownership checks must happen in the Route Handler, Server Action, or Server Component where the data lives — a user can hit those directly, bypassing middleware.

✅ Key takeaways

  • Store sessions in httpOnly cookies; gate cheaply in middleware; enforce for real on the server.
  • Authentication = who you are; authorization = what you're allowed to do (check both).

Environment Variables

Server env vars stay secret; only NEXT_PUBLIC_* variables are exposed to the browser bundle.

.env.local
DATABASE_URL=postgres://...        # server only — never shipped to client
STRIPE_SECRET=sk_live_...          # server only
NEXT_PUBLIC_API_URL=https://api... # exposed to the browser (build-time inlined)
Critical mistake: putting a secret in a NEXT_PUBLIC_ variable or reading a server secret inside a Client Component — it gets inlined into the JS bundle and is public. Secrets must only be read in server code.

Security

Next.js closes some holes (JSX escaping, server-only secrets) but you own the rest.

  • XSS: JSX auto-escapes; never use dangerouslySetInnerHTML with untrusted input (sanitize with DOMPurify).
  • Server Action / Route Handler abuse: validate (Zod) + authenticate + authorize every one.
  • Secrets: server-only env; never in NEXT_PUBLIC_ or client components.
  • Cookies: httpOnly, Secure, SameSite; CSRF protection for cookie-based mutations.
  • Headers/CSP: set security headers in next.config.js or middleware (CSP, HSTS, X-Frame-Options).
  • Rate limiting: protect auth + mutation endpoints (edge middleware + a store like Redis).
  • Open redirect / SSRF: validate user-supplied URLs before redirecting or fetching.
OWASP mindset: treat every Server Action and Route Handler as a public, untrusted entry point — the same discipline you'd apply to an Express route.

Rendering Lifecycle & Timeline

The single most valuable mental model: exactly what happens, in order, from a URL to an interactive page. Memorize this timeline — most Next.js questions are "where in this pipeline does X happen?"

Request (URL) ↓ Middleware (edge: auth gate, redirects, rewrites, headers) ↓ Route Matching (map URL → app/ segments; layouts nest) ↓ Server Component Render (run async components on the server) ↓ Data Fetch (fetch/DB) ──▶ Cache lookup (memo → data cache) ↓ HTML + RSC Payload (HTML for instant paint; Flight payload describes the tree) ↓ Stream to Browser (chunked; Suspense boundaries flush as they resolve) ↓ Hydration (Client Components attach state + event handlers) ↓ Interactive
Read it as two halves: the server half (middleware → render → data → HTML/RSC) produces content fast and SEO-friendly; the client half (stream → hydrate) makes it interactive. Static routes skip the per-request server work (served from cache/CDN); dynamic routes run it every request.

✅ Key takeaways

  • Order: middleware → routing → server render → data/cache → HTML+RSC → stream → hydrate → interactive.
  • Static = precomputed; dynamic = per-request; PPR = static shell + streamed dynamic holes.

RSC & React 19 Internals

Beyond "Server Components render on the server" — how they actually reach the browser, and how React 19 powers Next.js.

The Flight protocol & RSC payload

The server doesn't send Server Components as HTML only. It serializes the rendered tree into a compact streaming format called the RSC Payload (the "React Flight" protocol) — a description of the component tree, their props, and placeholders (references) for Client Components. The browser uses it to reconcile with the HTML and to know where Client Components go.

Browser ↓ (navigates / requests) Client Component (reference only) ↓ Flight request Server Component Tree (rendered on server) ↓ serialize RSC Payload (tree + props + client-component references) ↓ stream to browser Reconcile with HTML → Hydration of Client Components only

Why hooks and event handlers aren't allowed in Server Components

  • Hooks (useState/useEffect): require a persistent instance that lives across renders in the browser. A Server Component runs once on the server and is gone — there's no client instance to hold state.
  • Event handlers (onClick): a function can't be serialized into the RSC payload and sent over the wire; interactivity must live in a Client Component that ships its own JS.
  • Serialization boundary: props passed from a Server to a Client Component must be serializable (no functions, class instances, etc.) — they cross the network.

React 19 features that make this work

React 19 APIRole in Next.js
async componentsServer Components can be async and await data directly.
use()Unwrap a promise/context in render (e.g. read a passed-down data promise in a client child). A React API, not a Next.js one.
Server Actions ("use server")Functions callable from the client that execute on the server.
useOptimistic, useFormStatusOptimistic UI & pending state around Actions.
Interview gold: "A Server Component is serialized to an RSC/Flight payload — a tree description with references to Client Components — streamed to the browser, which hydrates only those client leaves. Hooks/handlers are impossible in Server Components because there's no persistent client instance and functions can't be serialized."

Hydration & Navigation Internals

Hydration is React attaching event listeners and state to the already-rendered server HTML so it becomes interactive without re-rendering it from scratch.

TermMeaning
HydrationAttach JS behavior to server HTML (reuse the DOM).
Partial hydrationOnly interactive islands (Client Components) hydrate — the RSC model is partial hydration by design.
Progressive hydrationHydrate pieces as they stream in / as needed, not all at once.
Hydration mismatchServer HTML ≠ first client render → React warns and may re-render.

Why hydration mismatches happen (and how to fix)

Any value that differs between server and client on first render causes a mismatch:

Mismatch sources
Date.now()      // time differs server vs client
Math.random()  // different value each render
window / navigator / localStorage  // don't exist on the server
// Fix: render such values in useEffect (client-only), or guard with a mounted flag,
// or use suppressHydrationWarning for intentionally-different content (e.g. a timestamp).

Navigation internals — why it feels instant

<Link> enters viewport ↓ Prefetch (fetch the route's RSC payload in the background) ↓ Router Cache (store it client-side) click ↓ Navigation (no full page load) ↓ Partial Rendering (only the changed segment re-renders; shared layouts stay)
Why it's fast: <Link> prefetches the destination, stores it in the client Router Cache, and on click only the changed route segment re-renders while shared layouts persist — no full reload, no re-fetch of unchanged shells.

The compiler (SWC) & bundling

Next.js compiles with SWC (a Rust-based compiler, ~20× faster than Babel) and bundles with webpack (or Turbopack, the Rust successor).

Server Action & Middleware Internals

How a Server Action executes

<form action={fn}> ↓ POST (to a generated, encrypted action ID — not a URL you write) Server Action runs on the server ↓ Mutation (DB write) ↓ revalidatePath / revalidateTag ↓ Updated UI streamed back (new RSC payload)
  • Action IDs: Next generates an encrypted reference to the function; the client never sees the code, only the ID it POSTs to.
  • Serialization: arguments and return values cross the wire, so they must be serializable.
  • Security: it's a public endpoint — always authenticate + validate (Zod) inside the action. Bind sensitive args on the server, don't trust client-passed IDs.

Middleware execution order

Incoming request ↓ headers / rewrites (config) ↓ redirects (config) ↓ middleware.ts (your code — runs on the edge, before routing) ↓ filesystem routes (static files, public/) ↓ dynamic routes (app/ pages, route handlers) ↓ Response
Keep middleware tiny: it runs on every matched request on the edge. Do cheap work (read a cookie, verify a JWT signature); never hit a database or do heavy compute there.

Server Action security internals

  • Encrypted action references: Next generates an encrypted ID/closure for each action; the client can only invoke it by ID and can't read or forge the server code.
  • Origin validation: Next checks the request Origin/Host against the app to block cross-site invocation (a built-in CSRF-style guard); still add your own CSRF token for cookie auth.
  • Serialization restrictions: only serializable args/returns cross the boundary — you can't smuggle functions; bind trusted values (e.g. the current user id) on the server, not from client input.
  • Replay/authorization: treat every call as a fresh untrusted request — re-verify session + RBAC and validate the body (Zod) every time.

🟢 Beginner

What is Next.js and why use it over plain React?

A React framework adding SSR, file-based routing, Server Components, caching, and an API layer — giving SEO, fast first paint, small bundles, and full-stack ability without stitching libraries together.

App Router vs Pages Router?

App Router (app/) is Server-Components-first with nested layouts, streaming, and Server Actions. Pages Router (pages/) is Client-Components-first with getServerSideProps/getStaticProps — mature but no new features.

How does file-based routing work?

Folders under app/ are URL segments; a page.tsx makes a segment public. [param] is dynamic, (group) organizes without affecting the URL.

🟡 Intermediate

SSR vs SSG vs ISR — how do you choose in the App Router?

By how you fetch: cached fetch → SSG; revalidate:N → ISR; no-store or cookies/headers → SSR. Static/ISR for shareable content, SSR for personalized/real-time.

What is streaming and how does Suspense enable it?

The server flushes HTML in chunks as data resolves; wrapping a slow subtree in <Suspense fallback> lets the shell paint immediately and the slow part stream in — improving TTFB/FCP.

What is PPR (Partial Prerendering)?

Serves a static shell instantly and streams the dynamic/personalized holes (wrapped in Suspense) — combining SSG speed with SSR freshness on the same page.

🔵 Senior / Architecture

Explain the four Next.js caches and how to invalidate each.

Request Memoization (per-render fetch dedupe), Data Cache (fetch results across users → revalidate/revalidateTag/no-store), Full Route Cache (rendered static routes → revalidatePath/redeploy), Router Cache (client, visited routes → router.refresh()/time).

What is the RSC / Flight payload?

A serialized streaming description of the Server Component tree (props + references to Client Components). The browser reconciles it with the HTML and hydrates only the client leaves. Functions/handlers can't be serialized — that's why they're client-only.

Edge vs Node runtime — trade-offs?

Edge = V8 isolate, Web APIs only, fast global cold starts — great for middleware/personalization but no native Node APIs/DB drivers. Node = full APIs + DB access, heavier cold start — the default for most pages/handlers.

Design authentication for a Next.js app.

httpOnly Secure SameSite session cookie; short access + rotating refresh tokens; cheap middleware gate at the edge; verify session + enforce RBAC inside Server Actions/Route Handlers where the data lives (middleware can be bypassed); CSRF for cookie-based mutations.

🟣 Debugging / Performance / Production

What causes a hydration mismatch and how do you fix it?

Server HTML differing from the first client render — usually Date.now(), Math.random(), or window/localStorage. Move such values to useEffect, guard with a mounted flag, or use suppressHydrationWarning.

Your page's LCP is high — how do you debug it?

Lighthouse for lab vitals; optimize the LCP element with next/image + priority; use next/font; cut client JS (Server Components, code-split); stream slow parts with Suspense; verify caching/ISR; Bundle Analyzer for bloat; Chrome Performance for long tasks (INP).

How does <Link> make navigation feel instant?

It prefetches the destination's RSC payload, stores it in the client Router Cache, and on click only the changed segment re-renders while shared layouts persist — no full reload.

📚 More core questions

What are React Server Components and what problem do they solve?

Components that render only on the server and ship no JavaScript to the client. They reduce bundle size, allow direct data/DB access without an API, and keep secrets server-side. Only interactive Client Components hydrate in the browser.

How do you choose between SSR, SSG, and ISR in the App Router?

By how you fetch: cached fetch → static (SSG); revalidate: N → ISR; no-store or reading cookies/headers → per-request SSR. Static/ISR for shareable content, SSR for personalized/real-time data.

Explain the Next.js caching layers.

Request Memoization (dedupes fetches in one render), Data Cache (fetch results across requests, revalidate/tags), Full Route Cache (rendered static routes), and the client Router Cache (visited routes). You invalidate with revalidateTag/revalidatePath, no-store, or router.refresh().

Server Actions vs Route Handlers — when do you use each?

Server Actions for your own app's form mutations (less boilerplate, progressive enhancement). Route Handlers for public APIs, webhooks, and non-form clients (mobile, third-party). Both must validate + authenticate on the server.

How does authentication work and why isn't middleware enough?

Store sessions in httpOnly cookies; middleware does a cheap gate (cookie present) at the edge. But middleware can be bypassed by hitting a Server Action/Route Handler directly, so you must re-verify authentication and authorization on the server where the data or mutation actually happens.

How do you keep the client bundle small?

Default to Server Components; push "use client" to the smallest interactive leaves; pass server content into client components via children; lazy-load heavy client components with next/dynamic; analyze the bundle.

What is streaming and how does Suspense enable it?

The server sends HTML in chunks as data resolves. Wrapping a slow subtree in <Suspense fallback> lets the shell render immediately and the slow part stream in later, improving TTFB/FCP. loading.tsx is a Suspense boundary around the whole page.

Common Next.js production mistakes?

Leaking secrets via NEXT_PUBLIC_/client components; over-fetching in waterfalls instead of Promise.all; relying on stale cached fetches when data must be live; trusting Server Action input; making everything a Client Component (huge bundles); using next/router instead of next/navigation.
