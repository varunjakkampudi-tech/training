What is Frontend System Design

Frontend system design is the practice of making architecture-level decisions for a web UI so it stays fast, scalable, reliable, accessible, and maintainable as features, data, and team size grow. It's coding zoomed out: not "how do I write this component" but "how do all the pieces fit, and where are the trade-offs?"

What / Why / the problem it solves

  • What: designing the component model, state & data flow, rendering strategy, network/caching layer, and delivery pipeline of a frontend — plus the cross-cutting concerns (perf, a11y, security, observability).
  • Why: small apps work however you build them; large apps fail on the things you didn't design — re-render storms, giant bundles, cache bugs, inaccessible UIs, unobservable errors.
  • Problem it solves: turns vague requirements ("build a news feed") into concrete, defensible technical decisions with known trade-offs.

Interview reality: a frontend system design round gives you a broad prompt ("design Twitter's feed", "design a photo gallery", "design Google Docs") and grades your process: clarify requirements → propose an architecture → justify trade-offs → go deep where asked.

✅ Key takeaways

  • Frontend SD = architecture-level decisions for a UI, judged on trade-offs, not syntax.
  • Its metrics are Core Web Vitals + bundle size + maintainability, not requests/sec.

The RADIO Framework (how to drive the interview)

A repeatable structure so you never freeze on an open-ended prompt. RADIO = Requirements → Architecture → Data model → Interface (API) → Optimizations.

StepWhat you do
R — RequirementsClarify functional (what it does) & non-functional (perf, a11y, devices, offline, scale). Ask questions; state assumptions.
A — ArchitectureBreak UI into components; define boundaries, data ownership, and rendering strategy. Draw a diagram.
D — Data modelClient-side entities/stores; normalized vs nested; what's server state vs UI state.
I — Interface / APIThe contract with the backend: endpoints, pagination shape, real-time channel, error format.
O — OptimizationsPerf (virtualization, code-split, caching), a11y, security, i18n, error handling — go deep where asked.
Prompt: "Design a news feed" ↓ Requirements (infinite scroll? real-time? images? offline? #users?) ↓ Architecture (Feed → FeedList → FeedItem; virtualized; data layer) ↓ Data model (posts normalized by id; cursor for pagination) ↓ Interface (GET /feed?cursor=..&limit=20; WS for new posts) ↓ Optimizations (virtualization, image lazy-load, optimistic likes, prefetch)
First 2 minutes matter most: spend them clarifying requirements. Jumping to components without pinning scope (real-time? scale? devices?) is the #1 reason candidates fail.

Scalability (frontend edition)

A frontend "scales" along axes the backend doesn't: more DOM nodes, more state, more code, more engineers. Each needs a strategy.

AxisSymptom at scaleTechnique

TrafficOrigin load, latencyCDN, caching, SSR/SSG, edge
Mental model: frontend scalability is about keeping three budgets under control as the app grows — the render budget (stay at 60fps), the network budget (bytes over the wire), and the cognitive budget (can a new engineer understand a feature in isolation?).

Performance & Core Web Vitals

Performance is measurable. Google's Core Web Vitals are the shared language; optimize to them.

MetricMeasuresGoodLevers
LCP (Largest Contentful Paint)Loading — biggest element painted< 2.5sFast server/CDN, optimize hero image/font, preload, SSR
INP (Interaction to Next Paint)Responsiveness< 200msLess JS, break up long tasks, web workers, debounce
CLS (Cumulative Layout Shift)Visual stability< 0.1Set image/embed dimensions, reserve space, font-display
TTFB / FCP / TTIServer, first paint, interactivity—Caching, streaming, hydration strategy

The RAIL model

Response — react to input in < 100ms Animation — produce a frame in < 16ms (60fps) Idle — use idle time for deferred work (requestIdleCallback) Load — deliver interactive content fast (< 5s on mid-tier mobile)
Measure, then optimize: lab tools (Lighthouse, WebPageTest) for repeatable diagnosis; field data (Real-User Monitoring / web-vitals library, CrUX) for what actual users experience. Never optimize blind.

✅ Key takeaways

  • LCP = loading, INP = responsiveness, CLS = stability. Learn the lever for each.
  • RAIL: 100ms response, 16ms frames, use idle time, fast load.

Browser Internals

You can't design a fast frontend without knowing what the browser actually does. A browser is several coordinated engines.

ComponentJob
NetworkingDNS, TCP/TLS, HTTP/2-3; fetch resources
HTML parserTokens → DOM tree
CSS engineParse CSS → CSSOM; compute styles
JS engine (V8, etc.)Parse/compile/run JS (the main thread)
Rendering / compositorLayout, paint, composite layers onto the GPU
Event loopCoordinates tasks, microtasks, rendering, and input

The single main thread

Main thread (one!) does: JS + style/layout/paint + event handling ↓ Long JS task → can't paint / respond → jank, high INP Fix: split work (yield), Web Workers (off-thread), rAF for visual updates
The core constraint: JS and rendering share one main thread. A long-running function blocks painting and input — the root cause of jank and poor INP. Everything in performance flows from this.

The Rendering Pipeline

How the browser turns HTML/CSS/JS into pixels — the "pixel pipeline". Knowing which steps a change triggers is how you avoid jank.

DOM + CSSOM → Render Tree → Layout (reflow) → Paint → Composite │ │ │ │ │ structure styles geometry (x/y/w/h) fill pixels GPU layers
StageWhat a change costs
Layout / reflowMost expensive — recompute geometry (changing width, top, reading offsetHeight)
PaintFill pixels (changing color, background, box-shadow)
CompositeCheapest — GPU moves layers (transform, opacity)
Golden perf rule: animate with transform and opacity only — they skip layout and paint (composite-only). Animating width/top/left triggers layout every frame and drops frames.
Layout thrashing: interleaving DOM reads (offsetHeight) and writes (style.height) in a loop forces synchronous reflows repeatedly. Batch reads, then writes (or use requestAnimationFrame).

Critical Rendering Path

The CRP is the minimum sequence of steps the browser must complete to show the first meaningful pixels. Shortening it = faster FCP/LCP.

HTML → parse → DOM CSS → parse → CSSOM (render-blocking!) JS → parse/run (parser-blocking unless async/defer) DOM + CSSOM → Render Tree → Layout → Paint → first pixels
BlockerFix
CSS is render-blockingInline critical CSS; load the rest async; minimize/split CSS
Synchronous JS blocks the parser<script defer> (run after parse) or async (run when ready); avoid render-blocking JS
Fonts cause FOIT/CLSfont-display: swap, preload, self-host
Big JS delays TTICode split, defer non-critical, SSR the shell
Interview one-liner: "To optimize the CRP I minimize and inline critical CSS, defer non-critical JS, preload the LCP image/font, and server-render the initial HTML so the browser paints before JS arrives."

Component Architecture

How you split the UI into components determines reusability, testability, and re-render cost. Two complementary models: presentational vs container, and atomic design.

PatternIdea
Presentational vs ContainerDumb UI (props in, events out) vs smart (data/logic). Keeps UI reusable & testable.
Atomic designatoms → molecules → organisms → templates → pages. Scales a component library.
Compound components<Tabs><Tab/></Tabs> share state via context — flexible APIs.
Headless componentsLogic + a11y with no styles (Radix, React Aria) — you own the look.
FeedPage (container: fetches data) └─ FeedList (organism, virtualized) └─ FeedItem (molecule) ├─ Avatar (atom) ├─ Text (atom) └─ LikeButton (client leaf, interactive)
Design decision: lift interactivity to the smallest leaf. A feed of 1000 items should have 1000 tiny interactive LikeButtons, not 1000 fully-interactive item components — smaller re-render surface, smaller bundle.
Common mistake: prop drilling data through many layers. Colocate state with where it's used, or use context/a store for truly global state — but don't put everything in one global store (see State Architecture).

Folder Architecture

Structure by feature, not by file type, so a feature is understandable and movable in isolation — critical for large teams.

❌ Type-based (breaks at scale)

Editing one feature touches many folders; hard to find/own.

✅ Feature-based (scales)

Rule: shared code goes up (components/ui, lib); feature code stays in its folder and exposes a small index.ts public API. Enforce boundaries with lint rules (no deep imports across features).

State Architecture

The most important frontend design decision. First, classify your state — different kinds need different tools.

State kindExampleWhere it lives
Server stateUsers, posts (from an API)React Query / SWR / RTK Query (cache + sync)
Global UI stateTheme, auth, cartContext / Redux / Zustand
Local UI stateInput value, modal openuseState in the component
URL stateFilters, tab, pageThe URL (searchParams) — shareable, back-button friendly
Form stateFields, validationReact Hook Form / Formik
#1 anti-pattern: putting server state in Redux and hand-writing loading/error/refetch. Use a server-cache library (React Query) — it handles caching, dedupe, background refetch, and stale-while-revalidate for you.

Normalization & selectors

For relational data, normalize (store entities by id, reference by id) to avoid duplication and keep updates O(1). Use memoized selectors (reselect) so components only re-render when their slice changes.

Normalized store
{
  posts: { byId: { 1: {id:1, author: 10}, 2: {...} }, allIds: [1,2] },
  users: { byId: { 10: {id:10, name: "Aria"} } }
}   // update user 10 once → every post referencing it is correct

✅ Key takeaways

  • Classify state (server / global UI / local / URL / form) and pick the right tool per kind.
  • Don't manage server state manually — use a caching data layer. Normalize relational data.
How do you decide where a piece of state should live?

Ask: is it from the server? → server-cache lib (React Query). Shared across the tree? → context/store. Used by one component? → local useState. Should it survive refresh / be shareable? → URL. Form? → a form library. Wrong placement (e.g. server data in Redux) causes most state bugs.

Data Flow

Predictable UIs use unidirectional data flow: data goes down (props), events go up (callbacks), a store is the single source of truth.

Store / server cache │ (state down) ▼ Components render │ user acts ▼ Dispatch action / mutation │ ▼ Store updates → components re-render (one direction, no surprises)

Optimistic updates

For snappy UX, update the UI before the server confirms, then roll back on failure — essential for likes, drag-and-drop, chat.

Optimistic like (React Query)
useMutation({
  mutationFn: like,
  onMutate: async (id) => {
    await qc.cancelQueries(["post", id]);
    const prev = qc.getQueryData(["post", id]);
    qc.setQueryData(["post", id], (p) => ({ ...p, liked: true })); // optimistic
    return { prev };
  },
  onError: (_e, id, ctx) => qc.setQueryData(["post", id], ctx.prev), // rollback
});
Interview point: optimistic UI trades correctness-latency for perceived speed. Always design the rollback path and reconcile with the server's real response.

Caching (every layer)

The fastest request is the one you don't make. The frontend touches several cache layers — know each.

Browser memory (JS: React Query cache, in-memory maps) ↓ miss Service Worker Cache (offline, precache, runtime cache) ↓ miss HTTP cache (Cache-Control, ETag, 304 Not Modified) ↓ miss CDN edge cache ↓ miss Origin server → Database
LayerControlled byUse
App/data cacheReact Query/SWR (staleTime, cacheTime)Dedupe, background refetch, SWR
Service WorkerCache API + strategiesOffline, instant repeat visits
HTTP cacheCache-Control, ETagStatic assets, API GETs
CDNCache headers + purgeGlobal, near-user delivery

Cache invalidation strategies

  • Stale-While-Revalidate: serve cached instantly, refetch in the background, swap in fresh — the default UX win.
  • Cache-busting: content-hashed filenames (app.9f3a.js) + long max-age for immutable assets.
  • Tag/key invalidation: after a mutation, invalidate the affected query keys so they refetch.
"There are only two hard things…": cache invalidation. Design how a cached value becomes stale before you cache it (time-based? event-based? version-based?).

API & Data Fetching Design

The client–server contract shapes your whole frontend. Design it deliberately.

ConcernOptions / guidance
StyleREST (simple, cacheable), GraphQL (flexible, avoids over/under-fetch), gRPC-web (perf)
Over-fetchingAsk for only needed fields (GraphQL) or design task-specific REST endpoints (BFF)
WaterfallsParallelize independent requests; prefetch on hover/route
ErrorsConsistent shape (code + message); handle loading/empty/error states in the UI
Real-timeWebSocket (bi-directional), SSE (server→client), polling (simple)
BFF pattern (Backend-for-Frontend): a thin API tailored to the UI that aggregates/reshapes microservice data — kills client-side waterfalls and over-fetching. Common in large frontends.
WebSocket vs SSE vs polling — how do you choose?

Polling: simplest, fine for low-frequency updates; wastes requests. SSE: one-way server→client stream over HTTP, auto-reconnect — great for feeds/notifications. WebSocket: full-duplex, low latency — needed for chat, collaboration, live cursors. Choose the least powerful option that meets the latency/direction needs.

Pagination

Loading huge lists in chunks. Two models: offset and cursor — the choice is a classic interview question.

Offset / page

  • ?page=2&limit=20 / ?offset=20
  • Simple; can jump to any page
  • Slow deep in large tables; items shift if data changes (duplicates/skips)

Cursor / keyset

  • ?cursor=<lastId>&limit=20
  • Stable & fast for large/real-time feeds
  • Opaque cursor; no random page jumps
Rule: use cursor pagination for feeds/infinite scroll (data changes underneath you), offset for admin tables where users pick page numbers.

Infinite Scroll

Load the next page as the user nears the bottom. Use IntersectionObserver (not scroll listeners) to detect the sentinel.

IntersectionObserver sentinel
const ref = useRef();
useEffect(() => {
  const io = new IntersectionObserver(([e]) => {
    if (e.isIntersecting) fetchNextPage();   // near bottom → load more
  }, { rootMargin: "200px" });        // prefetch before fully visible
  if (ref.current) io.observe(ref.current);
  return () => io.disconnect();
}, []);
// <div ref={ref} /> sentinel at the end of the list
Combine with virtualization: infinite scroll keeps appending DOM — after thousands of items the page dies. Pair it with virtualization (§18) so only visible rows are in the DOM. Also preserve scroll position and provide a "back to top" + real footer access.

🌍 Real-world

Twitter/Instagram feeds = cursor pagination + IntersectionObserver + virtualization + optimistic likes + image lazy-load. This combination is a canonical frontend SD answer.

Search & Autocomplete (Typeahead)

A staple machine-coding + system-design question. It combines debouncing, caching, cancellation, and a11y.

keystroke → debounce(300ms) → cache hit? ─yes→ show │ no ▼ cancel in-flight request (AbortController) ▼ fetch /search?q=... → cache by query → render → highlight
  • Debounce input so you don't fire per keystroke.
  • Cancel stale requests (AbortController) so a slow old response can't overwrite a newer one (race condition).
  • Cache results by query string; instantly serve repeats.
  • a11y: role="combobox", aria-activedescendant, arrow-key navigation, announce result counts.
  • Backend: prefix index / trie / search engine (Elasticsearch); return ranked, minimal fields.
The classic race bug: "reactjs" results arrive after "react" results and overwrite them. Fix by cancelling stale requests or ignoring responses whose query no longer matches the current input.

Debounce & Throttle

Both limit how often a function runs — the difference is when.

Debounce

Runs after activity stops for N ms. Use: search input, resize, autosave.

debounce
function debounce(fn, d) {
  let t;
  return (...a) => { clearTimeout(t); t = setTimeout(() => fn(...a), d); };
}

Throttle

Runs at most once per N ms. Use: scroll, mousemove, drag, rapid clicks.

throttle
function throttle(fn, l) {
  let wait = false;
  return (...a) => { if (wait) return;
    fn(...a); wait = true; setTimeout(() => wait = false, l); };
}
Pick by intent: "do it once the user finishes" → debounce. "do it steadily but not too often" → throttle. Scroll-driven UI = throttle; search = debounce.

Virtualization (Windowing)

Render only the rows currently in (and near) the viewport, no matter how many total. The single most important technique for large lists/tables.

10,000 items, viewport shows ~15 ↓ virtualization DOM contains ~20 rows (visible + buffer) ↓ scroll recycle: unmount rows that leave, mount rows that enter ↓ absolutely position rows; a tall spacer preserves scrollbar height
How it works: a container of the full scroll height (totalItems × rowHeight) with only the visible slice absolutely positioned. As you scroll, compute the start index from scrollTop and render that window. Libraries: react-window, react-virtuoso, TanStack Virtual.

Hard parts: variable row heights (measure & cache), scroll restoration, keyboard access, and find-in-page (Ctrl+F won't find off-DOM rows). Weigh these before virtualizing.

✅ Key takeaways

  • Virtualization caps DOM nodes to the viewport → constant render cost regardless of list size.
  • It's the answer to "how do you render 100k rows?" — pair with infinite scroll + cursor pagination.

Lazy Loading

Load resources only when needed — components, images, routes, data.

WhatHow
ComponentsReact.lazy(() => import("./X")) + <Suspense>
RoutesPer-route dynamic import (route-based code splitting)
Images / iframesloading="lazy", IntersectionObserver
DataFetch on demand / on interaction / on visibility
Prefetch on intent: lazy-load by default, but prefetch the likely-next chunk on hover/focus/idle so the click still feels instant. Lazy ≠ slow if you prefetch smartly.

Code Splitting & Bundling

Ship less JS up front by splitting the bundle into chunks loaded on demand. Fewer bytes → faster TTI/INP.

One big bundle (2MB) → slow parse/execute → high TTI ↓ split route chunks + vendor chunk + lazy feature chunks ↓ initial load ships only the current route's JS; rest loads on navigation
  • Route-based splitting — biggest win; each route is a chunk.
  • Component-based — split heavy widgets (charts, editors, maps).
  • Tree shaking — bundler drops unused exports (needs ES modules, sideEffects:false).
  • Vendor/runtime chunking — cache stable deps separately from your changing code.
  • Bundle budgets — fail CI if a chunk exceeds a size threshold.
Common mistake: importing a huge library for one function (e.g. all of lodash/moment). Import submodules (lodash/debounce) or use lighter alternatives (date-fns). Analyze with a bundle analyzer.

Asset Optimization

JS, CSS, fonts, and images are bytes over the network. Shrink and sequence them well.

AssetTechnique
JS/CSSMinify, compress (Brotli/gzip), code-split, remove dead CSS (PurgeCSS)
FontsSelf-host, subset, font-display: swap, preload, WOFF2, variable fonts
Loading orderpreload critical, prefetch next, preconnect to origins, defer JS
TransferHTTP/2-3 multiplexing; long cache + content hashing for immutables
Resource hints cheat sheet: preconnect (warm a connection to an origin), preload (fetch a critical resource now), prefetch (fetch a likely-next resource at low priority), dns-prefetch (resolve DNS early).

Image Optimization

Images are usually the largest bytes on a page and the most common LCP element. Optimizing them is the highest-ROI performance work.

Original 4MB JPEG ↓ resize to displayed size (responsive srcset) ↓ modern format (AVIF/WebP by Accept header) ↓ compress (quality ~75) ↓ lazy-load below the fold; priority-load the LCP image ↓ set width/height (no CLS) → serve from CDN
  • Responsive: srcset/sizes serve the right resolution per device (don't ship a 2000px image to a phone).
  • Format: AVIF/WebP over JPEG/PNG; SVG for icons.
  • No CLS: always set width/height (or aspect-ratio); use a blur/LQIP placeholder.
  • LCP: preload/priority the hero image; lazy-load the rest.
Framework help: next/image and image CDNs (Cloudinary, imgix) automate resize + format + CDN. Roll-your-own = an image proxy + CDN.

CDN & Edge Delivery

A Content Delivery Network caches your assets on servers around the world so users download from a nearby edge, not a distant origin.

User (Tokyo) → nearest CDN edge (Tokyo) ──cache hit──▶ instant │ miss ▼ Origin (US) → fill edge cache → serve
  • Static assets (JS/CSS/images/fonts) — served from the edge with long cache + content hashing.
  • Edge compute — run logic (auth, A/B, personalization, SSR) at the edge for low latency.
  • Benefits: lower latency, less origin load, DDoS absorption, TLS termination.
Cache strategy: immutable hashed assets → Cache-Control: max-age=31536000, immutable. HTML → short TTL or revalidate so deploys go live. Purge the CDN on deploy for anything cached long.

Accessibility (a11y)

An accessible design decision, not an afterthought. Bake in semantics, keyboard support, and ARIA where native HTML falls short.

  • Semantic HTML first — button/nav/main give roles + keyboard behavior free.
  • Keyboard — everything operable via Tab/Enter/Space/Arrows; visible focus; no traps (except modals).
  • ARIA — for custom widgets follow the APG patterns (combobox, tabs, dialog); ARIA adds semantics, not behavior.
  • Screen readers — labels, alt text, live regions for async updates.
  • Contrast & motion — WCAG AA 4.5:1; respect prefers-reduced-motion.
System-design angle: a design system with accessible primitives (or headless libs like Radix/React Aria) makes every feature accessible by default — the scalable way to "do a11y" across a big org.

Offline Support & PWA

A Service Worker is a background script that proxies network requests, enabling offline, caching, and push — the core of a Progressive Web App.

Page ⇄ Service Worker (proxy) ⇄ Cache API / Network │ strategies: cache-first (assets) · network-first (API) stale-while-revalidate (best of both)
  • Precache the app shell at install → instant repeat loads & offline.
  • Runtime caching strategies per route/resource type.
  • Background sync — queue failed mutations (e.g. a sent message) and replay when back online.
  • Manifest + HTTPS → installable app; push notifications.
Gotcha: Service Workers cache aggressively — a bad SW can serve stale code forever. Version your caches, clean old ones on activate, and have an update flow (skipWaiting + reload prompt).

Monitoring & Error Tracking

You can't fix what you can't see. Production frontends need real-user monitoring and error tracking.

SignalTooling

ErrorsSentry: JS exceptions + source maps + user/session context, error boundaries

Error boundaries catch render errors in a subtree and show a fallback (React componentDidCatch / error.tsx) — pair with Sentry so users see a graceful UI while you get the stack trace.

Feature Flags & Experimentation

Ship code dark, release with a flag. Decouple deploy from release for safe rollouts, A/B tests, and instant kill-switches.

  • Release flags — gradually roll a feature to 1% → 100%; roll back instantly on issues.
  • Experiment flags — A/B test variants, measure impact.
  • Permission/entitlement flags — gate by plan/role.
  • Ops flags / kill switches — disable a broken feature without a deploy.
Design considerations: evaluate flags without flicker (server-render the correct variant to avoid a flash), avoid shipping both variants' heavy code to everyone (split by flag), and clean up stale flags (they become tech debt). Tools: LaunchDarkly, Unleash, Statsig.

Micro-Frontends

Split a large app into independently-built, independently-deployed pieces owned by different teams — the frontend analog of microservices.

ApproachHow
Build-timePackages composed at build (simple, but coupled deploys)
Run-time (Module Federation)Webpack MF loads remote bundles at runtime — independent deploys
Iframe / Web ComponentsStrong isolation; integration/UX cost
Route-based (shell)A shell app routes to team-owned sub-apps
Trade-off: micro-frontends solve an organizational scaling problem (many teams), at the cost of duplicated dependencies, version skew, and integration complexity. Don't adopt them for a single small team — the overhead outweighs the benefit.

✅ Key takeaways

  • Micro-frontends = independent deploys per team; use Module Federation for runtime composition.
  • They're an org-scaling tool, not a default — they add real integration cost.

Design Systems

A shared library of accessible, themeable components + design tokens + guidelines — the way large orgs ship consistent UI fast.

  • Design tokens — colors/spacing/typography as named values; one source of truth, themeable.
  • Primitives — accessible Button, Input, Modal, Menu (often headless + styled).
  • Docs — Storybook: browse, test, and document components in isolation.
  • Versioning — semver the package; a change ripples to every consumer, so test thoroughly.
Why it's a system-design topic: a design system is how you keep 50 engineers producing consistent, accessible, performant UI without re-solving buttons and modals in every feature. It encodes your a11y and perf decisions once.

Internationalization & Real-Time

i18n / l10n

  • Externalize strings (no hard-coded text); load locale bundles on demand (don't ship all languages).
  • Formatting — Intl APIs for dates/numbers/currency/plurals per locale.
  • RTL — logical CSS properties (margin-inline-start) + dir="rtl"; mirror layouts.

Real-time UI

Transport: polling < long-polling < SSE < WebSocket Use cases: notifications (SSE) · chat/collab (WS) · presence/cursors (WS) Concerns: reconnection/backoff, ordering, dedupe, optimistic + reconcile, conflict resolution (CRDT/OT for collaborative editing)
Collaboration (Google-Docs-style): concurrent edits need conflict resolution — OT (Operational Transform) or CRDTs — plus presence, cursors, and offline reconciliation. A staff-level topic worth naming in interviews.

Real-World Case Studies

Apply the framework to canonical prompts. For each: requirements → architecture → data → optimizations.

📰 Design a News Feed (Twitter / Facebook)

Requirements: infinite feed, real-time new posts, images, likes, offline-ish Architecture: FeedPage → VirtualizedList → FeedItem(LikeButton leaf) Data: posts normalized by id; cursor pagination; WS for new posts Optimizations: virtualization + cursor infinite scroll, image lazy-load + LCP priority, optimistic likes, prefetch next page, skeletons, SWR cache

🔎 Design an Autocomplete / Typeahead

debounce(300ms) → cache by query → cancel stale (AbortController) → fetch ranked results → highlight match → combobox a11y (arrows, aria-activedescendant) Backend: trie/prefix index or search engine; return top-N minimal fields

🖼️ Design an Image Gallery / Pinterest grid

Masonry/virtualized grid → responsive srcset + AVIF/WebP → lazy-load + LQIP blur → CDN delivery → infinite scroll (cursor) → set dimensions (no CLS) → priority the LCP tile

📝 Design a Collaborative Editor (Google Docs)

WebSocket transport → CRDT/OT for concurrent edits → presence + remote cursors → optimistic local apply + server reconcile → offline queue + sync → autosave (debounced)
How to shine: state the requirements & assumptions, draw the component + data diagram, then go deep on the 1–2 areas the interviewer probes (usually virtualization/pagination for feeds, or conflict resolution for editors).

Interview Questions

🟢 Fundamentals

How does the browser render a page (pixel pipeline)?

Parse HTML→DOM and CSS→CSSOM, combine into the render tree, run Layout (geometry), Paint (pixels), then Composite (GPU layers). Layout is most expensive; compositing (transform/opacity) is cheapest.

What is the Critical Rendering Path and how do you optimize it?

The minimum steps to first paint. Optimize by minimizing/inlining critical CSS, deferring non-critical JS (defer/async), preloading the LCP image/font, and server-rendering the initial HTML.

reflow vs repaint vs composite?

Reflow/layout recomputes geometry (expensive); repaint fills pixels (medium); composite moves existing GPU layers (cheap). Animate transform/opacity to stay composite-only.

🟡 Patterns

How do you render a list of 100,000 items?

Virtualization/windowing — only render the ~20 rows in/near the viewport with a tall spacer for scroll height, recycling rows as you scroll. Pair with cursor pagination + infinite scroll for the data.

Offset vs cursor pagination?

Offset (page/limit) is simple and allows page jumps but is slow deep in large tables and shifts items when data changes. Cursor (keyset) is stable and fast for feeds/real-time but can't jump to arbitrary pages. Use cursor for feeds, offset for admin tables.

Design autocomplete — what are the key concerns?

Debounce input, cancel stale requests (AbortController) to avoid race conditions, cache results by query, combobox a11y (arrow keys, aria-activedescendant), and an efficient backend index (trie/search engine). Handle loading/empty/error states.

Debounce vs throttle — when each?

Debounce runs after activity stops (search, autosave, resize). Throttle runs at most once per interval (scroll, mousemove, drag). "Do it when they finish" → debounce; "do it steadily" → throttle.

🔵 Architecture

How do you classify and place state?

Server state → React Query/SWR; global UI → context/store; local UI → useState; shareable (filters/tabs) → URL; forms → a form lib. Don't manage server state manually in Redux.

How do you keep a large frontend maintainable across many teams?

Feature-based folders with enforced boundaries, a shared design system + tokens, typed contracts, and (at org scale) micro-frontends with independent deploys. Encode a11y/perf once in the design system.

How do you make navigation feel instant?

Route-based code splitting + prefetch the next chunk/data on hover/idle, cache with SWR, optimistic updates for mutations, and skeletons/streaming so the shell paints immediately.

🟣 Performance & Production

Your app feels janky (poor INP) — how do you debug?

Long main-thread tasks block input. Profile with Chrome Performance to find long tasks; break them up (yield, scheduler), move heavy work to a Web Worker, debounce/throttle handlers, virtualize lists, and ship less JS (code-split). Animate transform/opacity only.

How do you improve LCP?

Fast TTFB (CDN/SSR), preload + priority the hero image, optimize its size/format (AVIF/WebP + srcset), self-host + preload the LCP font, and remove render-blocking CSS/JS. Set dimensions to avoid CLS.

How do you make a frontend observable?

RUM with the web-vitals library (field LCP/INP/CLS), error tracking (Sentry + source maps + error boundaries), breadcrumbs/tracing with correlation IDs to the API, and alerts on regressions.

When would you NOT use micro-frontends?

For a single small/medium team — the org-scaling benefit doesn't justify the cost of duplicated deps, version skew, and integration complexity. Prefer a modular monolith with feature folders + a design system.
