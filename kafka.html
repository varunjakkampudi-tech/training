What is Kafka & Why It Exists

Apache Kafka is a distributed, durable, high-throughput event-streaming platform. At its core it's a replicated, append-only commit log that lets many producers write events and many consumers read them independently — at millions of events per second.

The problem it solves: as systems grow, you get an N×M integration mess — every service calling every other service, each with its own format, retries, and coupling. Kafka inverts this: producers publish events to durable topics; any number of consumers subscribe independently. It becomes the central nervous system for data, decoupling who produces from who consumes.

Before Kafka (point-to-point spaghetti): After Kafka (hub): A ─▶ B A ─▶ C A ─▶ D A ─┐ ┌─▶ B B ─▶ C B ─▶ D C ─▶ D (N×M links) B ─┼▶[KAFKA]┼─▶ C ...every service wired to every other... C ─┘ └─▶ D producers write once; consumers read independently
Kafka shines for…Because…
Decoupling services (pub/sub)Producers and consumers evolve independently; add consumers anytime
Real-time pipelines & analyticsStream events to warehouses, search, dashboards with low latency
Event sourcing / audit logsThe log is durable, ordered, and replayable — replay history anytime
High-throughput ingestionMetrics, clickstreams, IoT — millions of events/sec, buffered durably
Stream processingKafka Streams/ksqlDB transform, join, aggregate streams in place

🌍 Who uses it

Born at LinkedIn (to move activity data), Kafka now runs at Netflix, Uber, Airbnb, Pinterest, and most large enterprises — trillions of messages a day. It's the de-facto standard for event streaming.

Event Streaming & the Log Abstraction

Everything in Kafka builds on one deceptively simple idea: the append-only log. Understanding it explains partitions, offsets, replay, and consumer groups all at once.

An event and a log

An event (or record/message) is an immutable fact that happened: "user 42 clicked", "order 99 paid". A log is an ordered, append-only sequence of these events. You can only add to the end; existing entries never change. Each entry gets a sequential offset (0, 1, 2, …).

The log (one partition): offset: 0 1 2 3 4 5 → (append here) event: [pay] [add] [pay] [ship] [add] [pay] ▲ oldest ▲ newest / log end Consumers track WHERE they are (their offset). Reading doesn't delete — different consumers read the same log at their own pace, and can rewind.

Why a log is so powerful

  • Durable & replayable: events persist (by time/size), so a new consumer can replay from offset 0 to rebuild state.
  • Decoupled: producers don't know or wait for consumers; consumers read independently.
  • Ordered: within a partition, order is guaranteed — critical for correctness.
  • Fast: sequential disk writes/reads are extremely fast (near memory speed) and OS page cache does the rest.
Log ≠ queue. A traditional queue deletes a message once consumed. Kafka's log retains events and lets many independent consumers read them — that's why it supports replay, multiple downstreams, and reprocessing.

Kafka Architecture

A Kafka cluster is a set of servers (brokers) that store the logs, plus a control plane that manages metadata and leadership.

KRaft mode (production-ready since Kafka 3.3, default in 4.0) removes the ZooKeeper dependency: a quorum of controllers runs Raft to store metadata internally. Fewer moving parts, faster failover, and far more partitions per cluster.

When to Use Kafka (and When Not To)

Kafka is powerful but operationally heavy. Reach for it when its strengths — durable, replayable, high-throughput, multi-consumer streams — actually matter.

Use Kafka when ✅
  • Many consumers need the same event stream independently.
  • You need replay/reprocessing or an event log as source of truth.
  • High, sustained throughput (metrics, clicks, IoT, CDC).
  • Building real-time pipelines / stream processing.
  • Decoupling many services via events.
Prefer something else when ⚠️
  • Simple task queue with per-message ack → RabbitMQ/SQS/Redis.
  • Low volume, few consumers → a lightweight broker.
  • Request/response RPC → gRPC/REST.
  • You can't run/operate a stateful cluster → managed service.
Kafka is not a database and not a low-latency RPC. It's a streaming log. Don't use it for point lookups, transactions across arbitrary keys, or as your only store of record for query-heavy access.

Topics

A topic is a named stream of events — the category you publish to and subscribe from (e.g. orders, clicks, payments). Topics are multi-producer and multi-consumer.

bash — create & inspect a topic
kafka-topics.sh --create --topic orders \
  --partitions 6 --replication-factor 3 --bootstrap-server localhost:9092
kafka-topics.sh --describe --topic orders --bootstrap-server localhost:9092
  • Partitions (next section) determine parallelism and ordering scope.
  • Replication factor = how many copies of each partition exist across brokers (durability).
  • Topics are cheap to create but each partition has cost — don't over-partition.
Naming: use clear, domain-oriented names (payments.captured, user.signup). Many teams adopt a convention like <domain>.<entity>.<event> for discoverability.

Partitions — the unit of parallelism

A topic is split into partitions, each an independent append-only log on a broker. Partitions are the most important concept: they give Kafka scalability, parallelism, and its ordering guarantee.

Topic "orders" with 3 partitions (each an independent log): P0: [o0][o3][o6][o9] ← ordered within P0 P1: [o1][o4][o7] ← ordered within P1 P2: [o2][o5][o8][o10] ← ordered within P2 Producers spread events across partitions (by key or round-robin). Each partition is consumed by ONE consumer in a group → parallelism = #partitions.
  • Parallelism: more partitions = more consumers can work in parallel. Max useful consumers in a group = number of partitions.
  • Ordering: Kafka guarantees order within a partition, not across the whole topic. Same-key events go to the same partition, so per-key order is preserved.
  • Scalability: partitions of one topic spread across brokers, so a topic's throughput scales with the cluster.
Choosing partition count is a big decision. Too few = limited parallelism/throughput. Too many = more overhead, longer failover, more open files. You can increase partitions later, but that changes key→partition mapping (breaking per-key ordering for existing keys) — so plan ahead. A common start: 6–12, sized to target throughput.

Offsets & the Commit Log

An offset is the position of an event within a partition — a monotonically increasing integer. Consumers use offsets to track "how far I've read", which is what enables replay and independent consumption.

Partition P0: offset: 0 1 2 3 4 5 6 ← log end offset (LEO) ▲ ▲ consumer-A here consumer-B here Each consumer group stores its committed offset per partition in the internal topic __consumer_offsets. Rewind = seek to an earlier offset.
TermMeaning
Current/committed offsetThe last offset a group confirmed it processed (resume point after restart)
Log-end offset (LEO)The next offset to be written — the tip of the log
Consumer lagLEO − committed offset = how far behind a consumer is (a key health metric)
High watermarkHighest offset safely replicated → the last offset consumers may read
Consumer lag is the single most important consumer metric. Rising lag means consumers can't keep up with producers → add consumers/partitions or speed up processing.

Brokers & the Cluster

A broker is a Kafka server. A cluster is many brokers working together, sharing the partitions of all topics. Clients connect to any broker (a "bootstrap" server) and discover the rest.

  • Partition leadership: each partition has one leader broker (handles all reads/writes) and follower replicas on other brokers.
  • Load spreading: leadership is balanced across brokers so no single broker is a hotspot.
  • Bootstrap: clients only need a few broker addresses; they fetch full metadata (who leads which partition) automatically.
Topic orders, 3 partitions, replication-factor 3: Broker1: P0(leader) P1(follower) P2(follower) Broker2: P0(follower) P1(leader) P2(follower) Broker3: P0(follower) P1(follower) P2(leader) Reads/writes for a partition go to its LEADER; followers replicate to stay in sync. Lose a broker → a follower is promoted → no data loss (if RF ≥ 2 & in-sync).
Reads normally go to the leader too (not followers) so consumers see a consistent, committed view. (Newer versions allow follower fetching for locality/rack-awareness.)

Replication & In-Sync Replicas (ISR)

Replication is how Kafka survives broker failures without losing data. Each partition is copied to multiple brokers; one is the leader, the rest are followers that continuously pull from the leader.

ISR — the in-sync replica set

The ISR is the set of replicas (including the leader) that are fully caught up with the leader. Only ISR members are eligible to become leader. A message is considered committed once all ISR members have it — and only committed messages are readable.

Partition P0, RF=3: Leader (B1) ───replicate──▶ Follower (B2) ✅ caught up ┐ ───replicate──▶ Follower (B3) ✅ caught up ├─ ISR = {B1,B2,B3} A slow/dead follower falls out of ISR. If ISR shrinks below min.insync.replicas, the leader refuses writes (with acks=all) to avoid data loss.
SettingEffect
replication.factorCopies per partition (3 is the durable default)
min.insync.replicasMin ISR members that must ack a write (2 with RF=3 tolerates one failure safely)
unclean.leader.electionfalse = never promote an out-of-sync replica (no data loss); true risks losing data for availability
Durable default: RF=3, min.insync.replicas=2, producer acks=all, unclean.leader.election=false. This tolerates one broker failure with zero data loss.

Retention

Unlike a queue, Kafka keeps events after they're consumed — for a configured retention period or size. This is what makes replay and multiple independent consumers possible.

SettingMeaning
retention.msKeep data for this long (e.g. 7 days = 604800000)
retention.bytesKeep at most this many bytes per partition
segment.ms / .bytesLog is split into segments; old whole segments are deleted
cleanup.policydelete (time/size) or compact (keep latest per key) or both
Retention is per-topic. High-volume raw events might keep 1–3 days; an audit/event-sourcing topic might keep forever (or use compaction). Tiered storage (offload old segments to object storage) lets you keep long history cheaply.

Log Compaction

Compaction is an alternative to time-based deletion: instead of dropping old events, Kafka keeps the latest value for each key. The result is a compacted log that always contains the current state of every key.

Before compaction (key=value): [a=1][b=1][a=2][c=1][b=2][a=3] After compaction (only the latest per key survives): [c=1][b=2][a=3] A "tombstone" (key with null value) marks a key for deletion.
Why it matters: compaction turns a topic into a durable, replayable key-value changelog. A new consumer can replay it to rebuild the latest state of every entity. This powers Kafka Streams state stores, config/reference-data topics, and CDC (change-data-capture).
Compaction keeps latest per key, not a full history. If you need every change (event sourcing), use cleanup.policy=delete with long retention, not compaction — or keep both a raw event topic and a compacted state topic.

Producers

A producer publishes events to a topic. It batches records, compresses them, chooses a partition, and sends them to the partition leader — asynchronously for throughput.

java — a producer
props.put("bootstrap.servers", "broker1:9092");
props.put("acks", "all");              // durability
props.put("enable.idempotence", true);  // no duplicates on retry
props.put("linger.ms", 10);            // wait to batch
props.put("compression.type", "lz4");
var p = new KafkaProducer<>(props);
p.send(new ProducerRecord<>("orders", order.id, order.json));
Tuning knobEffect
batch.size + linger.msBigger batches = higher throughput, slightly higher latency
compression.typelz4/zstd cut network & disk dramatically
acksDurability vs latency (§14)
max.in.flight.requestsParallel unacked batches; keep ≤5 with idempotence to preserve order

Partitioning & Keys (ordering)

How a producer picks a partition determines both load balance and ordering. The message key is the lever.

  • With a key: partition = hash(key) % numPartitions. All events with the same key land on the same partition → per-key ordering is guaranteed.
  • Without a key: records are spread (sticky/round-robin) for even load, but no ordering across them.
key = orderId → hash → same partition for that order order:42 events → all to P1 → processed IN ORDER (created→paid→shipped) order:99 events → all to P2 → their own order preserved Different orders parallelize across partitions; each order stays ordered.
Key skew = hot partition. If one key (or a few) dominate traffic, its partition becomes a bottleneck while others idle. Choose a high-cardinality, evenly-distributed key (e.g. userId/orderId), not something like country.

Acknowledgements & Durability (acks)

The acks setting is the core durability-vs-latency trade-off: how many replicas must confirm a write before the producer considers it successful.

acksGuaranteeTrade-off
0Fire-and-forget; no ackFastest; can silently lose messages
1Leader wrote itFast; lost if leader dies before replicas copy it
all (-1)All in-sync replicas have itSafest (no loss with min.insync.replicas≥2); slightly slower
Rule of thumb: for anything you can't afford to lose (payments, orders), use acks=all + min.insync.replicas=2 + RF=3. For lossy, high-volume telemetry where speed > completeness, acks=1 can be acceptable.

Idempotent & Transactional Producers

Retries can create duplicates: a producer sends a batch, the ack is lost, it resends — now the event is written twice. Idempotent and transactional producers fix this.

Idempotent producer (no duplicates)

enable.idempotence=true assigns each producer a PID and each message a sequence number. The broker dedupes retries per partition, guaranteeing exactly-once writes to a partition even with retries. It's cheap and on by default in modern Kafka — always keep it on.

Transactional producer (atomic multi-partition writes)

Transactions let a producer write to multiple partitions/topics atomically — all appear or none do. This is the foundation of exactly-once stream processing (read → process → write, atomically with offset commits).

java — a Kafka transaction
producer.initTransactions();
producer.beginTransaction();
producer.send(rec1);  producer.send(rec2);   // to different topics
producer.sendOffsetsToTransaction(offsets, groupMeta); // atomic with consume
producer.commitTransaction();               // all-or-nothing
Consumers must opt in: to only see committed transactional data, set isolation.level=read_committed — otherwise they'd read aborted messages too.

Consumers

A consumer reads events from partitions, tracking its offset. It pulls in batches (poll loop) and processes them, then commits progress.

java — a consumer poll loop
props.put("group.id", "order-processors");
props.put("enable.auto.commit", false);   // commit manually
consumer.subscribe(List.of("orders"));
while (running) {
  var records = consumer.poll(Duration.ofMillis(100));
  for (var r : records) process(r);
  consumer.commitSync();                    // commit AFTER processing
}
The poll loop must keep polling. If processing a batch takes longer than max.poll.interval.ms, the broker thinks the consumer died and triggers a rebalance. For slow work, reduce max.poll.records or process asynchronously.

Consumer Groups & Rebalancing

A consumer group is a set of consumers that cooperatively read a topic — Kafka splits the partitions among them so each partition is read by exactly one member. This is how Kafka scales consumption and load-balances.

Topic with 4 partitions, group "workers" with 2 consumers: Consumer-1 ── P0, P1 Consumer-2 ── P2, P3 (each partition → one consumer) Add a 3rd consumer → REBALANCE → P0,P1 | P2 | P3 Add a 4th → one each. Add a 5th → it sits IDLE (partitions = max parallelism). Different GROUPS each get the FULL stream independently (pub/sub fan-out).
  • Scale out: add consumers (up to #partitions) to process faster.
  • Fault tolerance: if a consumer dies, its partitions are reassigned to survivors.
  • Fan-out: multiple groups on the same topic each receive all events (analytics + billing + search can all consume orders).
Rebalances are disruptive: during a rebalance, processing pauses ("stop-the-world"). Frequent rebalances (from slow processing, scaling, or crashes) hurt throughput. Mitigate with cooperative/incremental rebalancing, static membership (group.instance.id), and right-sized max.poll.records/timeouts.

Offset Management

When and how a consumer commits its offset decides your delivery semantics — and whether a crash causes duplicates or lost messages.

StrategyBehavior
Auto-commit (enable.auto.commit=true)Commits periodically in the background — simple but can commit before processing finishes (risk of loss)
Manual after processing (commitSync)Commit once work is done → at-least-once (a crash before commit reprocesses)
Commit before processingAt-most-once (a crash after commit skips the message)
Transactional (offsets in the tx)Exactly-once with the transactional producer
Default to at-least-once + idempotent processing: commit after you've handled the records, and make your handler idempotent (dedupe by event ID / upsert) so reprocessing after a crash is harmless. This is simpler and more robust than chasing exactly-once everywhere.

Delivery Guarantees

Three levels, chosen by how you configure producers, consumers, and offset commits.

GuaranteeMeaningHow
At-most-onceMay lose, never duplicatesCommit offset before processing; acks=0/1
At-least-onceNever lose, may duplicateacks=all + commit after processing (the common default)
Exactly-onceNever lose, never duplicateIdempotent + transactional producer + read_committed (EOS)
Exactly-once has a scope. Kafka's EOS covers Kafka-to-Kafka processing (read → transform → write atomically). The moment you touch an external system (a DB, an email API), you're back to needing idempotent writes. Most real systems use at-least-once + idempotent consumers.

Message Ordering

Kafka guarantees order within a partition, never across a whole topic. Design your keys and partitions around the ordering you actually need.

  • Per-entity order: key by the entity (orderId, userId) so all its events share a partition and stay ordered.
  • Global order: only achievable with a single partition — which sacrifices parallelism. Rarely truly required.
  • Preserve order under retries: with idempotence on, keep max.in.flight.requests.per.connection ≤ 5; without idempotence, a retry can reorder within a partition.
Interview answer: "Kafka orders within a partition. To keep per-customer events ordered, I key by customerId so they hash to one partition; different customers parallelize across partitions. I avoid needing global ordering because it forces a single partition."

Serialization (Avro, Protobuf, JSON)

Kafka moves bytes; producers serialize objects to bytes and consumers deserialize. The format you choose affects size, speed, and — crucially — schema evolution.

FormatProsCons
JSONHuman-readable, universal, easyVerbose, no enforced schema, larger
AvroCompact binary, rich schema evolution, Registry-friendlyNeeds schema tooling
ProtobufCompact, fast, strong typing, cross-languageNeeds .proto + tooling
For real pipelines, use Avro or Protobuf with a Schema Registry — smaller messages and, more importantly, safe schema evolution so producers and consumers can change independently without breaking each other.

Schema Registry & Evolution

The Schema Registry stores and versions the schemas for your topics and enforces compatibility rules, so a producer can't publish data that breaks existing consumers.

Producer ──register/lookup schema──▶ Schema Registry ◀──lookup── Consumer Message on the wire = [magic byte][schema ID][Avro/Protobuf payload] Consumer reads the ID → fetches the exact schema → deserializes correctly. Registry REJECTS an incompatible new schema before it can break consumers.
Compatibility modeRule
BACKWARD (default)New schema can read old data → consumers upgrade first
FORWARDOld schema can read new data → producers upgrade first
FULLBoth directions — safest, most restrictive
Safe evolution rules of thumb: add optional fields with defaults; never rename or change a field's type in place; deprecate rather than delete. The registry enforces this automatically so a bad deploy fails fast instead of corrupting downstream.

Kafka Connect

Kafka Connect is a framework for streaming data between Kafka and other systems without writing code — using ready-made connectors. It's how most data gets into and out of Kafka at scale.

Source connectors Sink connectors DB / files / CDC ──▶ [ Connect ] ──▶ Kafka ──▶ [ Connect ] ──▶ ES / S3 / DB / DW (Debezium captures DB changes) (index, archive, load warehouse)
  • Source connectors pull data in (databases via Debezium CDC, files, cloud services).
  • Sink connectors push data out (Elasticsearch, S3, Snowflake, JDBC, BigQuery).
  • Distributed & fault-tolerant: Connect runs as a cluster of workers that balance and restart tasks; it tracks offsets so it resumes safely.

🌍 CDC is the killer app

Debezium (a source connector) reads a database's transaction log and streams every insert/update/delete into Kafka. That powers the Outbox pattern, cache invalidation, search indexing, and keeping microservices' data in sync — all without dual writes.

Kafka Streams

Kafka Streams is a Java library for building stream-processing apps that read from Kafka, transform/aggregate/join, and write back — with state, windowing, and exactly-once, all as an ordinary app (no separate cluster).

java — word count topology
builder.stream("text")
  .flatMapValues(v -> List.of(v.split(" ")))
  .groupBy((k, word) -> word)
  .count()                       // stateful aggregation
  .toStream().to("word-counts");
ConceptMeaning
KStreamAn unbounded stream of records (events)
KTableA changelog view — latest value per key (a table from a compacted stream)
State storesLocal RocksDB, backed by a compacted changelog topic for fault tolerance
WindowingAggregate over time windows (tumbling, hopping, session)
Stream–table duality: a stream of changes and a table of current state are two views of the same data. Kafka Streams (and ksqlDB) exploit this to join streams with tables and materialize real-time views.

ksqlDB — stream processing in SQL

ksqlDB lets you build stream-processing pipelines with SQL instead of Java — filter, transform, join, and aggregate Kafka topics using familiar queries.

sql — a streaming aggregation
CREATE STREAM orders (id VARCHAR, amount DOUBLE)
  WITH (kafka_topic='orders', value_format='JSON');

CREATE TABLE revenue AS
  SELECT id, SUM(amount) AS total
  FROM orders WINDOW TUMBLING (SIZE 1 HOUR)
  GROUP BY id EMIT CHANGES;
When to use it: ksqlDB is great for quick real-time transformations, filtering, joins, and materialized views without building a Java app. For complex custom logic or tight control, Kafka Streams (or Flink) gives more power.

Performance Tuning

Kafka is built for throughput. Most tuning is about batching, compression, partitioning, and letting the OS page cache do its job.

LeverWhy it helps
Batching (batch.size, linger.ms)Fewer, bigger requests → far higher throughput
Compression (lz4/zstd)Less network & disk; often improves total throughput
Enough partitionsParallelism for producers and consumer groups
Zero-copy + page cacheKafka serves reads straight from OS cache via sendfile
Consumer fetch.min.bytes/max.poll.recordsBigger fetches amortize overhead; tune to processing speed
Fast disks (SSD) & enough RAMSequential writes + large page cache = low latency
Why Kafka is fast: sequential append-only writes, OS page cache for reads, zero-copy transfer (sendfile) from disk to socket, and batching/compression. It rarely needs exotic tuning to hit millions of messages/sec.

Security

A production Kafka must secure three things: who can connect (authentication), who can do what (authorization), and data in transit (encryption).

LayerMechanism
EncryptionTLS/SSL for client↔broker and inter-broker traffic
AuthenticationSASL (SCRAM, GSSAPI/Kerberos, OAUTHBEARER) or mTLS client certs

Never expose an unsecured broker. Enable TLS + SASL + ACLs, restrict network access, and follow least-privilege (a service can only touch its topics/groups). Managed offerings (Confluent Cloud, MSK) configure much of this for you.

Cluster Design & Sizing

Sizing a cluster is about throughput, retention, replication overhead, and failure tolerance — with headroom so a broker loss doesn't tip you over.

  • Brokers: start with at least 3 (so RF=3 and quorum works); scale out for throughput/storage.
  • Replication factor 3 for durability; min.insync.replicas=2.
  • Partitions: size to target throughput and max consumer parallelism; avoid tens of thousands per broker.
  • Storage: retention × ingest rate × RF, plus headroom; consider tiered storage for long retention.
  • Rack/AZ awareness: spread replicas across racks/zones so one zone failure doesn't lose a partition.
Rough capacity model: storage/broker ≈ (ingest_MB/s × retention_seconds × RF) / num_brokers + headroom max parallelism per group = partitions; throughput scales with partitions & brokers keep spare capacity so losing 1 broker doesn't overload the rest

Scaling

Kafka scales along a few axes. Knowing which to turn is a common design question.

To scale…Do this
Producer/consumer throughputAdd partitions (more parallelism) + more consumers in the group
Storage & total bandwidthAdd brokers; reassign partitions to balance
Number of independent readersAdd consumer groups (each gets the full stream)
Long retention cheaplyTiered storage (offload old segments to object storage)
Partitions bound consumer parallelism. A group can't have more active consumers than partitions — extras sit idle. If you're maxed out, add partitions (mindful that it changes key→partition mapping for existing keys).

Failure & Recovery

Kafka is designed to survive failures. Knowing what happens on each failure is core interview material.

FailureWhat Kafka does
Broker diesController elects a new leader from ISR for its partitions; producers/consumers reconnect — no data loss if RF≥2 & in-sync
Consumer diesGroup rebalances; its partitions go to surviving members; resumes from committed offset
Producer fails mid-sendRetries (idempotent → no dupes); unacked writes may need resend
Controller diesA new controller is elected (KRaft quorum / ZooKeeper)
Network partitionReplicas out of sync leave ISR; writes may pause (acks=all) to protect durability
Durability contract: with RF=3, min.insync.replicas=2, acks=all, and unclean.leader.election=false, Kafka tolerates one broker failure with zero acknowledged-message loss.

Multi-Region & Disaster Recovery

For DR and geo-distribution, you replicate data between clusters in different regions.

ApproachUse
MirrorMaker 2Async replication of topics + offsets between clusters (active-passive DR or aggregation)
Cluster Linking (Confluent)Byte-for-byte replication preserving offsets — simpler failover
Stretch clusterOne cluster across nearby AZs/regions with synchronous replication (low-latency links only)
Active-Passive DR: Region A (active) ──MirrorMaker2──▶ Region B (standby) Failover: point producers/consumers at B (offset translation keeps them close) Trade-off: async replication → some in-flight data may lag at failover (RPO > 0)
Define RPO/RTO first. Async replication (MM2) is simpler but can lose the last-lagging messages on failover; synchronous stretch clusters minimize loss but need low-latency links between regions.

Kafka is the backbone for several architecture patterns you'll design and be asked about.

🌍 The outbox pattern in practice

Instead of "write to DB and publish to Kafka" (a risky dual write), a service writes the business change and an outbox row in one DB transaction; Debezium reads the DB log and publishes the event — so the event is emitted if and only if the data was committed.

Retries & Dead Letter Queues

Some messages can't be processed (bad data, a downstream is down). You need a strategy so one poison message doesn't block a partition forever.

  • Retry topics: on failure, publish the message to a orders.retry.5m topic consumed after a delay; escalate through longer delays.
  • Dead Letter Queue (DLQ): after N failed attempts, route the message to a orders.DLQ topic for inspection/replay — so processing continues.
  • Don't block the partition: never infinitely retry in place; that stalls every later message in the partition (head-of-line blocking).
consume → process ──fail──▶ retry topic (delay) ──fail again──▶ ... ──▶ DLQ └── succeed → commit offset, move on DLQ is inspected/fixed and messages are replayed back into the main topic.
Kafka Connect has built-in DLQ support (errors.tolerance=all + errors.deadletterqueue.topic.name). For app consumers, libraries like Spring Kafka provide retry/DLQ out of the box.

Exactly-Once Semantics (EOS) — deep dive

EOS guarantees each record affects the result exactly once, even with retries and failures — within Kafka. It's built from three pieces working together.

EOS = Idempotent producer + Transactions + read_committed consumers read (offsets) ──┐ process ├── ALL committed in ONE transaction (atomic) write results ──┘ If the app crashes mid-transaction → the tx aborts → nothing is visible → on restart it reprocesses cleanly. No duplicates, no loss (Kafka→Kafka).
  • Idempotent producer removes duplicate writes to a partition on retry.
  • Transactions make multi-partition writes + offset commits atomic.
  • read_committed consumers ignore aborted messages.
  • Kafka Streams enables it with one setting: processing.guarantee=exactly_once_v2.
The boundary problem: EOS is a Kafka-internal guarantee. Writing to an external DB or calling an API is not covered — make those writes idempotent (idempotency keys, upserts) or use a sink connector that supports EOS. In practice: at-least-once delivery + idempotent side effects is the pragmatic, robust default.

Interview Questions

🟢 Fundamentals

What is Kafka and how is it different from a traditional message queue?

Kafka is a distributed, durable commit log for event streaming. Unlike a queue that deletes a message once consumed, Kafka retains events by time/size and lets many independent consumers read (and replay) them. Consumers track their own offset. This enables multiple downstreams, reprocessing, and event sourcing.

What is a partition and why does it matter?

A partition is an independent append-only log within a topic. Partitions provide parallelism (each is consumed by one member of a group), scalability (spread across brokers), and ordering (guaranteed within a partition). Partition count sets the max consumer parallelism.

How does Kafka guarantee ordering?

Only within a partition. Records with the same key hash to the same partition, so per-key order is preserved; different keys parallelize across partitions. Global ordering requires a single partition (sacrificing parallelism) and is rarely needed.

🟡 Reliability & Delivery

Explain acks and how you prevent data loss.

acks=0 = fire-and-forget (can lose), acks=1 = leader-only (lost if leader dies before replication), acks=all = all in-sync replicas (safe). For no loss: acks=all + min.insync.replicas=2 + RF=3 + idempotent producer + unclean.leader.election=false.

At-most-once vs at-least-once vs exactly-once — how do you achieve each?

At-most-once: commit offset before processing. At-least-once: acks=all + commit after processing (common default; make handlers idempotent). Exactly-once: idempotent + transactional producer + read_committed consumers (EOS) — but only within Kafka; external writes still need idempotency.

What is the ISR and what does it do?

The in-sync replica set — replicas fully caught up with the leader. A message is committed (and readable) once all ISR members have it; only ISR members can become leader. If ISR drops below min.insync.replicas, writes with acks=all are refused to avoid data loss.

🔵 Consumers & Scaling

How do consumer groups scale consumption?

Kafka assigns each partition to exactly one consumer in a group, so adding consumers (up to the partition count) increases parallelism; beyond that, extras idle. Separate groups each receive the full stream (fan-out). If a consumer dies, its partitions rebalance to survivors.

What is a rebalance and why is it a problem?

Reassignment of partitions when group membership changes (join/leave/timeout). During a (stop-the-world) rebalance, processing pauses. Frequent rebalances hurt throughput; mitigate with cooperative rebalancing, static membership, and keeping poll-loop processing within max.poll.interval.ms.

What is consumer lag and why monitor it?

Lag = log-end offset − committed offset, i.e. how far behind a consumer is. Rising lag means consumers can't keep up with producers; you add consumers/partitions or speed processing. It's the single most important consumer health metric.

🟣 Design & Ecosystem

When would you choose Kafka over RabbitMQ?

Kafka for high-throughput, durable, replayable streams with many independent consumers and stream processing (event sourcing, pipelines, CDC). RabbitMQ for classic task queues with flexible routing, per-message acks, and lower volume. It's about streaming log vs smart broker.

How do you evolve message schemas safely?

Use Avro/Protobuf with a Schema Registry that enforces compatibility (BACKWARD/FORWARD/FULL). Add optional fields with defaults, never rename/retype in place, deprecate instead of delete — so producers and consumers upgrade independently without breaking.

How do you handle a message that keeps failing?

Don't retry in place forever (it blocks the partition). Use retry topics with increasing delays, and after N attempts route to a Dead Letter Queue for inspection/replay, so the consumer keeps making progress.
