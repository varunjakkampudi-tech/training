What is Redis & Why It Exists

Redis (REmote DIctionary Server) is an open-source, in-memory data structure store used as a database, cache, message broker, and streaming engine. It keeps data in RAM for microsecond access and offers rich data types far beyond a plain key-value store.

The problem it solves: traditional disk-based databases (Postgres, MySQL) are durable but slow for hot, high-frequency access — every read may hit disk, parse SQL, and lock rows. Many workloads need answers in under a millisecond: session lookups, feature flags, counters, rate limits, leaderboards, real-time feeds. Redis puts that hot data in memory with purpose-built structures so those operations are effectively free.

Redis is great as…Because…
A cache in front of a databaseSub-millisecond reads offload the primary DB and cut latency 10–100×
A session/token storeFast shared state lets you run stateless, horizontally-scaled app servers
A rate limiterAtomic counters + TTL enforce limits across many app instances
A leaderboard / rankingSorted sets rank millions of scores in log time
A queue / streamLists and Streams move jobs and events with consumer groups
A pub/sub busReal-time fan-out for chat, notifications, live dashboards
The one-line pitch: Redis is a data-structure server. You don't just store bytes — you manipulate lists, sets, sorted sets, hashes, and counters directly on the server, atomically, at RAM speed.

🌍 Who uses it

Twitter (timelines), GitHub (job queues), Stack Overflow (caching), Instagram, Uber, Pinterest, Snapchat — nearly every large-scale system uses Redis somewhere in the hot path. It is consistently one of the most-loved databases in developer surveys.

The In-Memory, Single-Threaded Model

Understanding Redis's execution model explains almost all of its behavior — why it's fast, why it's atomic, and why one bad command can stall everything.

In-memory first, disk second

Redis holds the entire dataset in RAM. Reads and writes never touch disk on the hot path (disk is used only for persistence snapshots/logs, in the background). That's why operations take microseconds, not milliseconds.

Single-threaded command execution

The core command loop runs on a single thread. Commands are processed one at a time, to completion. This sounds like a limitation but is a superpower:

  • No locks, no race conditions — every command is inherently atomic; there's no concurrent mutation of the same key.
  • Predictable performance — no context-switching or lock contention overhead.
  • Simple mental model — commands appear to run in a strict sequence.
┌─────────────── single event loop ───────────────┐ clients ──▶ [socket] ──▶ parse ──▶ EXECUTE command ──▶ reply ──▶ [socket] (atomic, to completion) I/O uses epoll/kqueue (event-driven); since Redis 6, extra threads handle NETWORK I/O only — command execution stays single-threaded.
The catch: because one thread runs everything, a single slow command blocks all others. Commands like KEYS *, big SORT, or SMEMBERS on a huge set can freeze the whole server for seconds. Prefer SCAN and keep per-command work O(small).

Why not multi-threaded?

Redis is usually network- and memory-bound, not CPU-bound. A single thread already saturates the network on most workloads (100K+ ops/sec). Multi-threading the command path would add lock complexity for little gain. To use more cores, run multiple Redis instances (sharding / Cluster).

🔑 Key Takeaways

  • All data lives in RAM → microsecond latency.
  • Single-threaded command loop → automatic atomicity, no locks.
  • One slow command blocks everything → avoid O(N) commands on big keys.
  • Scale across cores with multiple instances, not threads.

Getting Started (redis-cli)

The fastest way to learn Redis is to type commands. redis-cli connects to a running server and speaks its simple text protocol (RESP).

bash — run & connect
# Run Redis locally (Docker is easiest)
docker run -d --name redis -p 6379:6379 redis:7

# Connect with the CLI
redis-cli            # connects to 127.0.0.1:6379
redis-cli -h host -p 6379 -a yourpassword
redis-cli — your first commands
SET user:1:name "Ada"      # store a string
GET user:1:name             # → "Ada"
EXPIRE user:1:name 60        # auto-delete after 60s
TTL user:1:name             # → 60 (seconds remaining)
EXISTS user:1:name          # → 1
DEL user:1:name             # → 1 (removed)
PING                        # → PONG (health check)
Key-naming convention: use object-type:id:field with colons, e.g. user:1000:session, cart:42:items. It keeps keys readable and groups related data for tooling.

Keys, Values & Time-To-Live (TTL)

Everything in Redis is stored under a key. Keys are binary-safe strings; values are one of the data types. TTL (expiration) is a first-class feature that makes Redis a natural cache.

Essential key commands

CommandPurpose
EXISTS keyDoes the key exist? (1/0)
DEL key [key…]Delete one or more keys
TYPE keyData type of the value (string, list, hash…)
EXPIRE key sec / PEXPIRESet TTL in seconds / milliseconds
TTL key / PTTLRemaining life; -1 = no expiry, -2 = gone
PERSIST keyRemove the TTL (make it permanent)
RENAME key newkeyRename a key
SCAN cursorIterate keys safely in batches (use this, not KEYS)
Never run KEYS * in production. It scans the entire keyspace in one blocking pass, freezing the server. Use SCAN 0 MATCH user:* COUNT 100 which returns a cursor and iterates in small, non-blocking chunks.
redis-cli — TTL & SCAN
SET otp:alice 123456 EX 300   # set + 5-min TTL in one atomic command
TTL otp:alice                    # → 300, counting down

# Iterate safely instead of KEYS *
SCAN 0 MATCH session:* COUNT 100  # → cursor + up to ~100 keys

🌍 TTL in practice

TTL powers OTP codes (expire in minutes), cached DB rows (expire in seconds/minutes), rate-limit windows (expire per window), and sessions (sliding expiry). Setting a TTL is how you stop a cache from growing forever.

Strings — the workhorse

The simplest type: a key maps to a single value (text, number, JSON, or binary up to 512 MB). Despite the name, strings back counters, bitmaps, and cached blobs.

CommandUse
SET / GETStore / fetch a value
SET k v EX 60 NXSet with TTL, only if not exists (great for locks)
MSET / MGETSet / get many keys in one round-trip
INCR / DECR / INCRBYAtomic counters (page views, IDs)
APPEND / GETRANGE / SETRANGEManipulate substrings
SETEX / GETDEL / GETEXSet-with-expiry / get-and-delete / get-and-set-TTL
redis-cli — counters are atomic
INCR page:home:views      # 1  (no read-modify-write race — atomic on the server)
INCRBY page:home:views 10  # 11
SET next_id 0
INCR next_id              # 1 → distributed, race-free ID generator
Why atomic counters matter: in a normal app you'd GET, add 1, SET — two clients can interleave and lose an update. INCR does it in one atomic server-side step, so concurrent increments are always correct.

Hashes — objects & records

A hash is a map of field → value under a single key — perfect for representing an object (a user, a product) without serializing the whole thing.

redis-cli — a user record
HSET user:1 name "Ada" age 36 city "London"
HGET user:1 name          # → "Ada"
HGETALL user:1            # → all fields+values
HINCRBY user:1 age 1      # → 37 (atomic field increment)
HDEL user:1 city          # remove one field
Hash per object ✅
  • Update one field without rewriting the whole object.
  • Memory-efficient for small objects (ziplist/listpack encoding).
  • Atomic field-level ops (HINCRBY).
JSON string per object
  • Must GET → parse → modify → SET the whole blob.
  • No field-level atomic updates.
  • Fine if you always read/write the whole object.
Memory tip: small hashes are stored compactly as a "listpack". Keeping objects as hashes (rather than one key per field) can save huge amounts of memory at scale — this is the classic Instagram optimization.

Lists — queues & stacks

A list is an ordered sequence of strings, implemented as a linked list. Push/pop at either end is O(1) — ideal for queues, stacks, and recent-activity feeds.

CommandUse
LPUSH / RPUSHAdd to head / tail
LPOP / RPOPRemove from head / tail
LRANGE k 0 -1Read a range (0..-1 = all)
LLENLength
BLPOP / BRPOPBlocking pop — wait for an item (worker queues)
LTRIM k 0 99Keep only the newest 100 (capped feed)
redis-cli — a simple job queue
# Producer pushes jobs
LPUSH jobs "send-email:42"
# Worker blocks until a job arrives, then processes it
BRPOP jobs 0            # 0 = wait forever; reliable FIFO with LPUSH+BRPOP
Reliable queues: plain BRPOP loses a job if the worker crashes mid-process. Use LMOVE/BLMOVE to atomically move the job to a "processing" list, then remove it on success — or better, use Streams (§12) with consumer groups and acks.

Sets — uniqueness & relationships

A set is an unordered collection of unique strings. Great for tags, unique visitors, and relationship math (friends-in-common, permissions).

redis-cli — set operations
SADD user:1:follows 2 3 4       # add members (dupes ignored)
SISMEMBER user:1:follows 3      # → 1 (fast membership test)
SCARD user:1:follows           # → 3 (count)
# Mutual follows = intersection of two sets
SINTER user:1:follows user:2:follows
SUNION a b   SDIFF a b     # union / difference

🌍 Unique counting

Track unique daily visitors: SADD visitors:2024-06-01 <userId>, then SCARD for the count. For huge cardinalities where exactness isn't required, switch to HyperLogLog (§11) to save memory.

Sorted Sets — ranking & ranges

A sorted set (ZSet) is a set where every member has a numeric score; members are kept ordered by score. This single structure powers leaderboards, priority queues, rate limiters, and time-series windows.

Internals: a ZSet combines a hash (member → score) with a skip list (ordered by score). That gives O(log N) inserts and O(log N) rank/range queries — fast even with millions of members.

redis-cli — a leaderboard
ZADD game:leaderboard 1500 alice 1800 bob 1200 cara
ZINCRBY game:leaderboard 300 cara        # cara → 1500
ZREVRANGE game:leaderboard 0 2 WITHSCORES  # top 3, high→low
ZREVRANK game:leaderboard bob            # → 0 (bob is #1)
ZRANGEBYSCORE game:leaderboard 1400 1600 # everyone in a score band
PatternHow the ZSet is used
Leaderboardscore = points; ZREVRANGE for top-N, ZREVRANK for a player's rank
Priority queuescore = priority/time; pop the lowest with ZPOPMIN
Sliding-window rate limitscore = timestamp; trim old, count remaining (§27)
Time series / recent itemsscore = epoch ms; ZRANGEBYSCORE for a time window
Why interviewers love ZSets: "design a leaderboard" is answered in one line — a sorted set gives ranking, top-N, and a player's rank all in log time, across millions of users.

Bitmaps — booleans at scale

Bitmaps aren't a separate type — they're bit operations on a string. Each bit is a flag, so you can track a yes/no fact for millions of users in a few KB.

redis-cli — daily active users
# bit at offset = userId; 1 = active today
SETBIT active:2024-06-01 1000 1
SETBIT active:2024-06-01 5000 1
GETBIT active:2024-06-01 1000     # → 1
BITCOUNT active:2024-06-01        # → 2 (total actives)
# Users active on BOTH days = AND of two bitmaps
BITOP AND result active:2024-06-01 active:2024-06-02
Memory magic: 1 million users × 1 bit = 125 KB. Tracking daily-active flags for a year is a few dozen MB — impossibly cheap versus a row per user per day.

HyperLogLog — count uniques with tiny memory

HyperLogLog (HLL) estimates the number of unique items in a stream using a fixed ~12 KB — regardless of whether you count thousands or billions, with ~0.81% error.

redis-cli — unique visitors, cheaply
PFADD visitors:home user:1 user:2 user:3
PFCOUNT visitors:home              # → ~3 (approximate)
# Merge multiple pages' uniques
PFMERGE visitors:all visitors:home visitors:blog
Set (exact)
  • Perfectly accurate count.
  • Memory grows with the number of unique items — huge for billions.
  • Use when you need the actual members or exactness.
HyperLogLog (estimate)
  • Fixed ~12 KB no matter the cardinality.
  • ~0.81% error; can't list members.
  • Use for "how many unique X" at massive scale (analytics).

Streams — logs, events & queues done right

A Stream is an append-only log of entries (like a mini Kafka inside Redis), with consumer groups, acknowledgements, and replay. It's the modern, reliable way to build queues and event pipelines on Redis.

redis-cli — produce & consume
# Producer appends events (auto ID with *)
XADD orders * user 42 total 99.90
# Create a consumer group starting at the beginning
XGROUP CREATE orders billing 0
# A worker reads new entries for its group
XREADGROUP GROUP billing worker1 COUNT 10 STREAMS orders >
# Acknowledge once processed (removes from pending)
XACK orders billing 1718000000000-0
ConceptMeaning
Entry ID<ms>-<seq>, monotonically increasing, sortable
Consumer groupA set of workers that split the stream; each entry goes to one member
PEL (pending list)Delivered-but-not-acked entries — enables retries after a crash
XCLAIM / XAUTOCLAIMReassign stuck entries from a dead worker to a live one
Streams ✅
  • At-least-once delivery with acks & retries.
  • Multiple independent consumer groups replay history.
  • Persisted, ordered, bounded via MAXLEN.
Pub/Sub ⚠️
  • Fire-and-forget — offline subscribers miss messages.
  • No history, no acks, no groups.
  • Fine for live-only fan-out (presence, live dashboards).

Geospatial — nearby search

Geo commands store longitude/latitude (internally as sorted-set scores via geohash) and answer "what's near me?" queries — the core of ride-hailing and store locators.

redis-cli — find nearby drivers
GEOADD drivers -0.1276 51.5072 "driver:7"   # London
GEOADD drivers -0.1180 51.5099 "driver:9"
# Drivers within 2 km of a point, nearest first
GEOSEARCH drivers FROMLONLAT -0.1250 51.5080 BYRADIUS 2 km ASC
GEODIST drivers driver:7 driver:9 km          # distance between two
Under the hood: geo is "just" a sorted set whose scores are 52-bit geohashes, so all ZSet operations still apply. Perfect for driver dispatch, "restaurants near you", and geofencing.

Pub/Sub — real-time fan-out

Publishers send messages to channels; subscribers listening on those channels receive them instantly. It's fire-and-forget broadcast — ideal for live features where missing an offline message is fine.

redis-cli — two terminals
# Terminal A — subscribe
SUBSCRIBE chat:room:1
# Terminal B — publish
PUBLISH chat:room:1 "hello everyone"   # delivered to all live subscribers
# Pattern subscribe (all rooms)
PSUBSCRIBE chat:room:*
No durability: Pub/Sub does not store messages. A subscriber that's disconnected when a message is published never sees it. For guaranteed delivery, retries, or replay, use Streams (§12). Redis 7 also adds sharded pub/sub (SPUBLISH) that scales in Cluster.

Transactions (MULTI / EXEC / WATCH)

Redis transactions queue several commands and run them as one isolated, sequential batch. Combined with WATCH, they enable optimistic-locking (compare-and-set) patterns.

redis-cli — atomic multi-command
MULTI                    # start queuing
INCR account:1:balance
DECR account:2:balance
EXEC                     # run all, atomically & in order

Optimistic locking with WATCH

redis-cli — safe compare-and-set
WATCH stock:42            # abort the tx if this key changes
# read stock in app; if > 0 continue
MULTI
DECR stock:42
EXEC                     # returns nil if stock:42 changed → retry
Not like SQL transactions: there is no rollback. If one command fails at runtime (e.g. wrong type), the others still execute. Redis guarantees isolation and atomic-batching, not all-or-nothing rollback. For true atomic logic, use a Lua script (§16).

Lua Scripting — atomic server-side logic

A Lua script runs on the Redis server atomically — no other command interleaves while it runs. This lets you implement complex, race-free logic (check-then-act) in a single round-trip.

Lua — atomic "set if greater"
-- KEYS[1] = key, ARGV[1] = new value
local cur = tonumber(redis.call('GET', KEYS[1]) or 0)
if tonumber(ARGV[1]) > cur then
  redis.call('SET', KEYS[1], ARGV[1])
  return 1
end
return 0
redis-cli — run & cache the script
EVAL "...script..." 1 highscore 2000
SCRIPT LOAD "...script..."    # → sha1; then EVALSHA sha 1 highscore 2000
When to reach for Lua: atomic rate limiters, "release lock only if I own it", conditional updates, and multi-step logic that must not interleave. Keep scripts short — remember they block the single thread while running.

Pipelining — batch to beat latency

Network round-trips dominate Redis latency. Pipelining sends many commands at once without waiting for each reply, then reads all responses — turning N round-trips into one.

Without pipeline: cmd1 → ← reply1 cmd2 → ← reply2 (N × RTT) With pipeline: cmd1,cmd2,cmd3 → ... ← reply1,reply2,reply3 (1 × RTT)
node — ioredis pipeline
const pipe = redis.pipeline();
for (const id of ids) pipe.get(`user:${id}`);
const results = await pipe.exec();  // one round-trip for all GETs
Pipeline vs transaction: pipelining is a network optimization (batch sending); it does not make commands atomic. MULTI/EXEC adds atomicity. You can combine them. For bulk-loading data, pipelining can be 5–10× faster.

Expiration & Eviction Policies

Two different mechanisms decide when keys disappear: expiration (TTL you set) and eviction (Redis removing keys when memory is full). Knowing both prevents surprise data loss and OOM crashes.

How TTL expiry actually works

  • Lazy expiry: when you access a key, Redis checks if it's expired and deletes it then.
  • Active expiry: a background job samples random keys ~10×/sec and removes expired ones so memory is reclaimed even for untouched keys.

Eviction policies (when maxmemory is hit)

PolicyBehavior
noevictionReject writes with an error (default) — safest for a datastore
allkeys-lruEvict least-recently-used key — classic cache choice
allkeys-lfuEvict least-frequently-used — better for skewed hot data
volatile-lru / -ttl / -lfuEvict only keys that have a TTL set
allkeys-randomEvict a random key
Cache vs database: if you use Redis purely as a cache, set maxmemory + allkeys-lru (or lfu) so it evicts cold data gracefully. If you use it as a source of truth, use noeviction and monitor memory — otherwise eviction silently deletes your data.

Persistence — RDB & AOF

Redis is in-memory, but it can survive restarts by writing to disk. There are two mechanisms with different durability/performance trade-offs — and you can combine them.

RDB (snapshots)
  • Point-in-time binary dump (dump.rdb) every N seconds/changes.
  • Compact, fast to load, great for backups.
  • Can lose the last few minutes of writes on crash.
  • Fork + copy-on-write can spike memory on big datasets.
AOF (append-only file)
  • Logs every write command; replayed on restart.
  • Far more durable (appendfsync everysec loses ≤1s).
  • Larger files, slower restart; auto-rewritten to compact.
Durability spectrum: RDB only → fast, may lose minutes of data AOF everysec → lose at most ~1 second (recommended default) AOF always → lose nothing, but fsync per write = slow RDB + AOF → RDB for fast restore + AOF for durability (best of both)
Recommended: enable both — RDB for quick full restores/backups and AOF (everysec) for minimal data loss. For a pure cache you can disable persistence entirely and rely on the source database to refill.

Memory Management & Optimization

RAM is the constraint that defines Redis capacity and cost. Understanding encodings and overhead lets you store far more in the same footprint.

CommandInsight
INFO memoryused_memory, maxmemory, fragmentation ratio
MEMORY USAGE keyBytes a specific key consumes
OBJECT ENCODING keyInternal encoding (listpack, intset, skiplist, hashtable…)
--bigkeys / MEMORY DOCTORFind large keys / get advice

Encoding matters

Small collections use compact encodings (listpack, intset) that pack data tightly. Once they exceed a threshold (e.g. hash-max-listpack-entries), they convert to a full hashtable/skiplist that uses more memory per element. Keeping objects small keeps them in the efficient encoding.

Big keys are dangerous: a single huge list/hash/set (millions of elements) causes slow O(N) commands, blocking, and uneven Cluster slots. Split large collections and monitor with redis-cli --bigkeys.
Fragmentation: a mem_fragmentation_ratio well above 1.0 means the allocator holds memory the dataset isn't using. activedefrag yes can reclaim it online.

Replication — read scaling & redundancy

A replica keeps a live copy of a primary (master). Replication gives you read scaling (serve reads from replicas) and a warm standby for failover.

writes ──▶ ┌──────────┐ clients │ PRIMARY │ reads ──▶ └────┬─────┘ async replication (command stream) ┌──────────┼──────────┐ ┌────▼───┐ ┌────▼───┐ ┌───▼────┐ │replica1│ │replica2│ │replica3│ ← serve reads here └────────┘ └────────┘ └────────┘
  • Asynchronous by default: the primary doesn't wait for replicas → fast writes, but a crash can lose the last un-replicated writes.
  • Full vs partial resync: a reconnecting replica resumes from a replication backlog if possible (partial), else does a full RDB transfer.
  • WAIT numreplicas timeout forces the client to wait until N replicas ack — tunable durability.
Replication lag = stale reads. Because replication is async, a read from a replica may not reflect the latest write. Read from the primary when you need read-your-writes consistency.

Sentinel — automatic failover (HA)

Replication alone doesn't promote a replica when the primary dies — a human would have to. Redis Sentinel is a separate process that monitors the primary, detects failure by quorum, and automatically promotes a replica.

┌─Sentinel─┐ ┌─Sentinel─┐ ┌─Sentinel─┐ (≥3, on separate hosts) └────┬─────┘ └────┬─────┘ └────┬─────┘ └── monitor & vote (quorum) ──┘ Primary DOWN → Sentinels agree → elect & promote a replica → update clients (they ask Sentinel "who is the master now?")
  • Monitoring: Sentinels ping the primary; if enough agree it's down (quorum), failover begins.
  • Election: Sentinels pick the best replica (most up-to-date) and REPLICAOF NO ONE promotes it.
  • Discovery: clients connect to Sentinels to learn the current primary — no hardcoded master IP.
Run an odd number (≥3) of Sentinels on separate machines so a single host failure can't take out both a Sentinel majority and the primary. Sentinel gives HA without sharding; Cluster (next) gives HA and horizontal scale.

Redis Cluster — horizontal scaling

A single Redis instance is limited by one machine's RAM and one core's throughput. Redis Cluster shards data across many primaries (each with replicas) so you scale memory and ops linearly.

Hash slots — how keys map to nodes

Cluster splits the keyspace into 16384 hash slots. Each key's slot is CRC16(key) mod 16384; slots are distributed across primaries. Resharding just moves whole slots — minimal, predictable data movement.

16384 slots divided across primaries: Node A: slots 0–5460 (+ replica A') Node B: slots 5461–10922 (+ replica B') Node C: slots 10923–16383 (+ replica C') key "user:42" → CRC16 → slot 9012 → lives on Node B Client is redirected (MOVED/ASK) to the owning node.
Multi-key ops must share a slot. Commands like MGET/SINTER across keys only work if the keys are on the same node. Use hash tags — {user:42}:profile and {user:42}:cart hash by the part in braces, forcing them onto the same slot.
Sentinel
  • HA for a single dataset (one primary + replicas).
  • No sharding — limited to one machine's RAM.
  • Simpler to run.
Cluster
  • HA + horizontal sharding across many primaries.
  • Scales memory & throughput; needs client support.
  • Multi-key/transaction constraints (same-slot).

Caching Patterns

Caching is Redis's #1 use case. The pattern you choose determines consistency, latency, and complexity.

PatternHow it worksTrade-off
Cache-aside (lazy)App checks cache; on miss, reads DB and populates cacheMost common; first request is slow; needs TTL/invalidation
Read-throughCache library loads from DB on miss transparentlyCleaner app code; needs cache that supports it
Write-throughWrite to cache and DB synchronouslyCache always fresh; slower writes
Write-behindWrite to cache, flush to DB asyncFast writes; risk of loss before flush
node — cache-aside
async function getUser(id) {
  const hit = await redis.get(`user:${id}`);
  if (hit) return JSON.parse(hit);          // cache hit
  const user = await db.findUser(id);        // miss → DB
  await redis.set(`user:${id}`, JSON.stringify(user), 'EX', 300);
  return user;
}
Invalidation is the hard part. "There are only two hard things in CS: cache invalidation and naming things." On write, either delete the cached key (let the next read repopulate) or update it. Pair every cached key with a sensible TTL as a safety net.

Cache Failure Modes (Stampede, Penetration, Avalanche)

At scale, caches fail in three classic ways. Interviewers ask about these by name — know the fix for each.

ProblemWhat happensFix
Stampede / thundering herdA hot key expires; thousands of requests miss at once and all hit the DBLock/singleflight so one request rebuilds; add jitter to TTLs; early recompute
PenetrationRequests for keys that don't exist bypass the cache and hammer the DBCache the "not found" (short TTL); Bloom filter to reject unknown keys
AvalancheMany keys expire at the same instant → DB spikeRandomize/stagger TTLs; layered caches; keep DB circuit-breakered
Hot keyOne key gets so much traffic it overloads its nodeLocal (in-process) cache in front; replicate the key; shard it
pattern — anti-stampede lock
# Only ONE request rebuilds the value; others wait or serve stale
SET lock:rebuild:home 1 NX EX 10   # NX = only if absent → winner rebuilds
# winner: recompute → SET cache → DEL lock; losers: brief wait/retry

Session Store

Storing sessions in Redis (instead of app memory) is what makes app servers stateless — any instance can serve any user, so you can scale horizontally and deploy without logging everyone out.

Browser (cookie: sessionId) ──▶ Load Balancer ──▶ any app instance │ GET session:<id> from Redis (shared state → instances are interchangeable)
redis-cli — a session with sliding expiry
HSET session:abc123 userId 42 role admin
EXPIRE session:abc123 1800          # 30-min idle timeout
# On each request: refresh TTL (sliding session)
EXPIRE session:abc123 1800
Why Redis for sessions: fast lookups on every request, built-in TTL for idle timeout, and shared across all servers. Popular middleware (connect-redis, Spring Session) uses exactly this.

Rate Limiter

Protect APIs from abuse by capping requests per user/IP per time window. Redis is the standard place to keep the shared counters so the limit holds across all gateway/app instances.

Fixed window (simplest)

redis-cli — N requests per minute
INCR rl:user:42:1718000000        # key includes the window timestamp
EXPIRE rl:user:42:1718000000 60     # window auto-expires
# if INCR result > limit → return HTTP 429

Sliding window (accurate) with a sorted set

Lua-style logic — sliding window
ZREMRANGEBYSCORE rl:user:42 0 (now-60000)   # drop entries older than window
ZADD rl:user:42 now now                       # record this request (score=timestamp)
ZCARD rl:user:42                              # count in window → compare to limit
EXPIRE rl:user:42 60
Do it atomically: wrap the check-and-increment in a Lua script so two concurrent requests can't both slip past the limit. The token-bucket algorithm (allow bursts, refill over time) is another common choice, also implemented in Lua.

Distributed Locks (Redlock)

When many processes might do the same job (send one email, charge once), you need a lock that works across machines. Redis provides a simple, fast distributed lock.

redis-cli — acquire & release safely
# Acquire: set only if absent, with a TTL so a crash auto-releases
SET lock:invoice:42 <randomToken> NX PX 10000   # NX + PX = safe lock

# Release: only if WE still own it (compare token) — via Lua for atomicity
# if GET lock == token then DEL lock end
  • NX ensures only one holder; PX TTL prevents a dead holder from locking forever.
  • Random token + Lua release ensures you only delete your lock, not one a slow process re-acquired.
Single-node caveat: a lock on one Redis is lost if that node fails during a failover. Redlock acquires the lock on a majority of N independent Redis nodes for stronger safety. Note: Redlock is debated for strict-correctness use cases — for money-critical mutual exclusion, prefer a fencing token + a consistent store. For most jobs, a single-node lock with TTL is fine.

Leaderboards

The canonical sorted-set use case: rank millions of players by score and answer "top 10" and "my rank" instantly.

redis-cli — full leaderboard
ZADD lb:global 4820 "player:7"          # set/update a score
ZINCRBY lb:global 50 "player:7"        # add points atomically
ZREVRANGE lb:global 0 9 WITHSCORES     # top 10
ZREVRANK lb:global "player:7"          # player's 0-based rank
ZCOUNT lb:global 4000 5000               # how many in a score band
Time-boxed boards: key by period — lb:2024-06, lb:weekly:2024-W23 — with a TTL so old boards expire. For "players near me", use ZREVRANK to find my position then ZREVRANGE rank-2 rank+2.

Job Queues (Lists & Streams)

Redis is a popular backbone for background jobs (emails, thumbnails, webhooks). You can build queues on lists (simple) or streams (reliable) — most production systems use a library on top.

List-based queue
  • LPUSH + BRPOP = simple FIFO.
  • Use LMOVE to a processing list for reliability.
  • No built-in acks/retries — you build them.
Stream-based queue
  • Consumer groups, acks (XACK), pending list, retries.
  • XAUTOCLAIM recovers jobs from dead workers.
  • The right choice for at-least-once delivery.

🌍 Libraries do the heavy lifting

BullMQ (Node), Sidekiq (Ruby), Celery (Python), RQ — all use Redis for queues, delayed jobs, retries, and dead-letter handling. You rarely hand-roll a production queue; you use these on top of Redis.

Security

Redis was designed for trusted networks, so security is opt-in. An exposed, unauthenticated Redis is one of the most-exploited misconfigurations on the internet.

ControlDo this
NetworkBind to private interfaces; firewall port 6379; never expose to the internet
AuthRequire a strong password (requirepass) and use ACLs for per-user, per-command permissions
TLSEnable TLS for client and replication traffic
Dangerous commandsrename-command to disable/rename FLUSHALL, CONFIG, KEYS, DEBUG
Protected modeKeep it on (blocks external access when no password/bind set)
redis-cli — ACL (least privilege)
ACL SETUSER app on >strongpass ~app:* +@read +@write -@dangerous
# user "app" can only touch app:* keys, read/write, no dangerous cmds
Never do this: run Redis bound to 0.0.0.0 with no password. Attackers scan for it, run CONFIG SET to write SSH keys or cron jobs, and take the host. Bind private + require auth + firewall.

Client Libraries & Connection Pooling

Your app talks to Redis through a client library. Configuring it well (pooling, timeouts, retries) is as important as the Redis config itself.

LanguagePopular clients
Node.jsioredis, node-redis

Gogo-redis
  • Pool connections: reuse a fixed set of connections; opening one per request destroys throughput and exhausts the server's maxclients.
  • Set timeouts: command + connect timeouts so a stalled Redis doesn't hang your app threads.
  • Handle failover: use a Sentinel-aware or Cluster-aware client so it follows the primary automatically.
  • Retry with backoff on transient errors; make retried operations idempotent.
RESP3 client-side caching: modern clients can cache hot values in the app process and let Redis push invalidations (tracking) — cutting network trips further for read-heavy keys.

Interview Questions

🟢 Fundamentals

Why is Redis so fast?

Data lives entirely in RAM (microsecond access), the command loop is single-threaded (no locks/contention, inherently atomic), it uses efficient data structures and an event-driven I/O model, and the RESP protocol is lightweight. It's typically network- or memory-bound, not CPU-bound.

Redis is single-threaded — isn't that a bottleneck?

Rarely, because it's usually network/memory-bound and a single thread already handles 100K+ ops/sec. Single-threading gives free atomicity and predictable latency. To use more cores you run multiple instances or Cluster. (Redis 6+ does use extra threads for network I/O, but command execution stays single-threaded.)

How does key expiration work internally?

Two mechanisms: lazy expiry (checked when a key is accessed) and active expiry (a background job samples random keys ~10×/sec and removes expired ones), so memory is reclaimed even for untouched keys.

🟡 Data & Patterns

How would you design a leaderboard?

A sorted set: ZADD/ZINCRBY to update scores, ZREVRANGE 0 9 for the top 10, ZREVRANK for a player's rank — all O(log N), scaling to millions. Time-box boards by keying on the period with a TTL.

Design a distributed rate limiter.

Keep counters in Redis so all instances share state. Fixed window: INCR a window-keyed counter with EXPIRE. Sliding window: a sorted set of request timestamps — remove old, add now, count. Wrap the check-and-increment in a Lua script for atomicity; return 429 + Retry-After.

String vs Hash for storing an object — which and why?

Hash if you update individual fields (field-level atomic ops, less memory via listpack encoding for small objects). A JSON string if you always read/write the whole object at once. Hashes avoid the get-parse-modify-set cycle.

Set vs HyperLogLog for counting uniques?

Set gives an exact count and the members but grows with cardinality — costly for billions. HyperLogLog gives an approximate count (~0.81% error) in a fixed ~12 KB and can't list members. Use HLL when you only need "how many unique" at massive scale.

🔵 Reliability & Scaling

RDB vs AOF — how do you choose?

RDB = periodic snapshots: compact, fast restore, but can lose minutes on crash. AOF = logs every write: far more durable (everysec loses ≤1s) but larger/slower. Best practice: enable both — RDB for fast restore/backups, AOF for durability. Pure caches can disable persistence.

Sentinel vs Cluster?

Sentinel adds automatic failover to a single primary+replicas set (HA, but no sharding — limited to one machine's RAM). Cluster shards data across many primaries via 16384 hash slots (HA + horizontal scale) but adds multi-key/same-slot constraints and needs a cluster-aware client.

How do you prevent a cache stampede?

When a hot key expires, use a rebuild lock (SET lock NX EX) so only one request recomputes while others wait or serve stale; add jitter to TTLs; optionally recompute early before expiry. Also guard against penetration (cache negatives) and avalanche (stagger TTLs).

How do Redis distributed locks work, and what are the pitfalls?

SET key token NX PX ttl to acquire (NX = only if absent, PX = auto-release on crash); release with a Lua script that deletes only if the token matches, so you don't delete someone else's lock. Pitfalls: single-node locks can be lost during failover — Redlock uses a majority of nodes, and for strict correctness a fencing token + consistent store is safer.
