Architecture Fundamentals

Backend system design is choosing how to arrange servers, data stores, queues, and networks so a system meets its non-functional requirements — scale, latency, availability, consistency, cost — not just "does it work".

The vocabulary

TermMeaning
LatencyTime for one request (p50/p95/p99 percentiles matter, not average)
ThroughputRequests processed per second (RPS/QPS)
Availability% uptime (99.9% = 8.7h/yr down; 99.99% = 52min/yr) — the "nines"
ConsistencyDo all readers see the same data? (strong vs eventual)
ScalabilityHandle more load by adding resources (vertical vs horizontal)
Reliability / Fault toleranceKeep working when components fail

Vertical vs horizontal scaling

Vertical (scale up)

  • Bigger machine (more CPU/RAM)
  • Simple; no code change
  • Hard limit; single point of failure; expensive

Horizontal (scale out)

  • More machines behind a load balancer
  • Near-limitless; fault-tolerant
  • Needs statelessness, coordination, data partitioning
Golden rule for scaling: make services stateless (session/state in a shared store like Redis/DB), then you can add identical instances behind a load balancer freely. State is the enemy of horizontal scale.

✅ Key takeaways

  • Design to non-functional requirements (scale, latency, availability, consistency, cost).
  • Prefer horizontal scaling + stateless services; measure latency at p95/p99, not average.

Back-of-the-Envelope Estimation

Interviews expect rough capacity math to justify your design. Learn the numbers and the method.

QuantityRule of thumb
Seconds/day~86,400 ≈ 10⁵
Read:write ratioOften 100:1 or more (read-heavy)
1 char1 byte; a tweet ≈ 300 bytes; a small image ≈ 200KB
QPS from DAUDAU × actions/day ÷ 86,400 (× 2–3 for peak)
Storage/yearwrites/day × size × 365
Example: design Twitter — capacity
300M DAU, each posts 2 tweets/day  → 600M writes/day
   writes QPS ≈ 600M / 86,400 ≈ 7,000  (peak ~2–3× → ~20,000)
reads 100× writes → ~700,000 read QPS  → need caching + read replicas + CDN
storage: 600M × 300B/tweet × 365 ≈ 65 TB/year (text)  → sharding needed
Method: DAU → QPS (peak) → storage/bandwidth → derive the components (cache, replicas, shards, CDN). State assumptions out loud; interviewers grade the reasoning, not the exact numbers.

Client–Server & the Request Path

Every backend design starts from the path a request takes. Know every hop.

Client → DNS → CDN (static/cache) → Load Balancer → API Gateway → Service(s) → Cache (Redis) → Database ↘ Message Queue → Workers (async jobs) ← response ← (observability: logs, metrics, traces at each hop)
  • DNS resolves the domain to an IP (often a load balancer / CDN edge).
  • CDN serves static assets & cached responses near the user.
  • Load balancer spreads traffic across service instances.
  • API gateway handles auth, rate limiting, routing, aggregation.
  • Services run business logic; cache shields the DB; queue defers slow work.
Design instinct: for any feature, ask "which hop does this belong in?" Auth → gateway; hot reads → cache; heavy/slow work → queue + workers; durable data → DB.

Monolith

One deployable app containing all features. The right default for most new products.

✅ Strengths

  • Simple to build, test, deploy, debug
  • No network between modules (fast, transactional)
  • One codebase, one CI/CD

⚠️ Weaknesses at scale

  • Whole app redeploys for any change
  • One bug can take down everything
  • Teams step on each other; scale the whole app, not hot parts
Modular monolith: a monolith with strict internal module boundaries. You get monolith simplicity now and an easy path to extract microservices later. Start here; don't build microservices you don't need yet.

Layered (N-Tier) Architecture

The default internal structure: separate concerns into horizontal layers so each is testable and swappable.

Controller / Route (HTTP: parse request, send response) ↓ Service / Domain (business rules — framework-agnostic) ↓ Repository / DAO (data access — hides the DB) ↓ Database
Why layers: controllers stay thin (HTTP only), services hold reusable business logic (unit-testable without a server), repositories isolate the database (swap Postgres→Mongo without touching business rules). Dependencies point downward only.

Clean Architecture

Concentric layers where dependencies point inward toward the domain. The core (entities, use cases) knows nothing about the web, the DB, or frameworks.

┌─────────────────────────────────────┐ │ Frameworks & Drivers (web, DB, UI) │ ← outer, replaceable │ ┌───────────────────────────────┐ │ │ │ Interface Adapters │ │ (controllers, gateways, presenters) │ │ ┌─────────────────────────┐ │ │ │ │ │ Use Cases (app logic) │ │ │ │ │ │ ┌───────────────────┐ │ │ │ │ │ │ │ Entities (core) │ │ │ │ ← inner, pure business rules │ │ │ └───────────────────┘ │ │ │ │ │ └─────────────────────────┘ │ │ │ └───────────────────────────────┘ │ └─────────────────────────────────────┘ Dependency Rule: source code dependencies point INWARD only.
Payoff: business rules don't depend on Express/Postgres, so you can test them in isolation and replace infrastructure without rewriting logic. Cost: more indirection/boilerplate — worth it for long-lived, complex domains, overkill for a CRUD app.

Hexagonal (Ports & Adapters)

The same idea as Clean, framed differently: the app core exposes ports (interfaces); the outside world plugs in via adapters.

[ HTTP adapter ] [ CLI adapter ] \ / ▼ ▼ (driving ports) → APPLICATION CORE ← (driven ports) ▲ ▲ / \ [ Postgres adapter ] [ Kafka adapter ]
  • Driving side (left) — things that call the app (HTTP, CLI, tests).
  • Driven side (right) — things the app calls (DB, message broker, email).
  • Swap any adapter (Postgres → Mongo, REST → gRPC) without touching the core.
Interview framing: Clean & Hexagonal both enforce "the domain depends on nothing; infrastructure depends on the domain via interfaces." Name-drop the Dependency Inversion Principle — that's the engine behind both.

Microservices

Split a system into small, independently-deployable services owned by different teams, each with its own database. Solves org + scaling problems — at real cost.

✅ Benefits

  • Independent deploy & scale per service
  • Team autonomy; tech per service
  • Fault isolation (one service down ≠ all down)

⚠️ Costs

  • Distributed systems complexity (network, partial failure)
  • Data consistency across services (no cross-DB transactions)
  • Ops burden: service discovery, tracing, deployment

Key patterns

ProblemPattern
Each service owns its dataDatabase-per-service
Transaction across servicesSaga (choreography/orchestration) + compensations
Read model spanning servicesCQRS + materialized views
Avoid dual-write bugsTransactional Outbox + CDC
One entry point for clientsAPI Gateway / BFF
Find servicesService discovery (DNS, Consul, K8s)
Don't start here. Microservices trade code complexity for operational complexity. Begin with a modular monolith; extract a service only when a clear scaling or team-ownership need appears. Premature microservices are a top cause of failed projects.
How do you handle a transaction across microservices?

You can't use a distributed ACID transaction at scale. Use a Saga: a sequence of local transactions where each step publishes an event triggering the next; if a step fails, run compensating transactions to undo prior steps. Use the Outbox pattern to publish events atomically with the DB write.

Communication: Sync vs Async

Two services can talk synchronously (request/response) or asynchronously (events/messages). Choosing well is core to a resilient design.

Synchronous (REST/gRPC)

  • Caller waits for a response
  • Simple, immediate result
  • Tight coupling; failures cascade; slower is slower

Asynchronous (queue/events)

  • Fire message, don't wait
  • Decoupled, resilient, absorbs spikes
  • Eventual consistency; harder to trace/debug
Rule of thumb: use sync when the caller needs the result now (fetch a profile). Use async for slow/optional/fan-out work (send email, generate thumbnail, update search index) — it keeps the request fast and the system resilient.

REST

Resources identified by URLs, manipulated with HTTP verbs. The default for public/web APIs — simple, cacheable, universally understood.

AspectBest practice
VerbsGET (read), POST (create), PUT/PATCH (update), DELETE
URLsNouns, plural: /users/42/orders
Status codes2xx ok, 4xx client, 5xx server; 201+Location on create
Versioning/v1/...; never break clients
IdempotencyGET/PUT/DELETE idempotent; use Idempotency-Key for POST
PaginationCursor for feeds, offset for admin
Strengths: HTTP caching, statelessness, tooling, simplicity. Weakness: over/under-fetching (fixed response shapes) — which is what GraphQL addresses.

GraphQL

A query language where the client asks for exactly the fields it needs from a single endpoint. Kills over/under-fetching and request waterfalls.

One request, exact shape
query {
  user(id: 42) {
    name
    orders(last: 5) { id total }   # only what you need, nested in one round trip
  }
}
✅ Good for⚠️ Watch out
Many clients, varied data needs (mobile+web)Caching is harder (POST, dynamic shapes)
Avoiding over/under-fetch & waterfallsN+1 queries (use DataLoader batching)
Strong typed schema + introspectionComplex/malicious queries (depth/cost limits)
The N+1 trap: resolving orders for 100 users can fire 100 DB queries. Batch with DataLoader (collect keys in a tick, one query) — the canonical GraphQL performance fix.

gRPC

A high-performance RPC framework using Protocol Buffers (binary) over HTTP/2. The default for internal service-to-service communication.

  • Fast & small: binary Protobuf + HTTP/2 multiplexing beats JSON/REST for throughput/latency.
  • Contract-first: a .proto schema generates typed client/server code in any language.
  • Streaming: client/server/bidirectional streams built in.
  • Weakness: not browser-native (needs gRPC-web + proxy); binary is less human-debuggable.
When to choose: internal microservice mesh where perf matters → gRPC. Public/browser API → REST (or GraphQL for flexible clients). Many systems use REST/GraphQL at the edge and gRPC between services.

Message Queues & Event Streaming

A broker between producers and consumers that decouples them, absorbs spikes, and enables async processing. The backbone of scalable, resilient backends.

Producer → [ Queue / Topic ] → Consumer(s) fast return buffer process at their own pace Benefits: decoupling · load leveling (spike absorption) · retries/DLQ · fan-out
TechModelUse
RabbitMQ/SQSQueue (message consumed once)Task/job processing, work distribution
KafkaLog/stream (replayable, many consumers)Event streaming, analytics, event sourcing
Redis StreamsLightweight streamSimple pub/sub + persistence
  • Delivery guarantees: at-most-once, at-least-once (dedupe with idempotency), exactly-once (hard, Kafka transactions).
  • Dead Letter Queue (DLQ): messages that fail repeatedly go here for inspection instead of blocking the queue.
  • Backpressure: if consumers lag, the queue buffers — size it and alert on lag.
Queue vs stream: a queue (SQS/RabbitMQ) deletes a message once processed — great for jobs. A log/stream (Kafka) retains events so multiple consumers can read and replay — great for events/analytics. (Kafka gets its own guide next.)

Caching

Store hot data closer/faster to cut latency and DB load. The highest-leverage backend optimization — and the trickiest to keep correct.

Browser → CDN → API cache (Redis) → Database each layer: hit = fast return; miss = go deeper, then populate the cache

Caching strategies

StrategyHowTrade-off
Cache-aside (lazy)App checks cache; on miss, load DB + populateMost common; first read is slow; possible stale
Read-throughCache loads from DB on miss itselfSimpler app code; needs cache support
Write-throughWrite to cache + DB togetherConsistent; slower writes
Write-backWrite to cache, async flush to DBFast writes; risk of loss on crash

Eviction & invalidation

  • Eviction: LRU (least recently used) is the default; also LFU, TTL expiry.
  • Invalidation: TTL (simple), or explicit delete/update on write (fresh but more code).
Three classic failures: Cache stampede (many misses hit the DB at once when a hot key expires → lock/singleflight or stagger TTLs), hot key (one key overwhelms a node → replicate/shard it), thundering herd on cold start (warm the cache).

✅ Key takeaways

  • Cache-aside is the default; pick write policy by consistency vs write-latency needs.
  • Design invalidation up front; defend against stampede, hot keys, and cold starts.

Redis (the backend swiss-army knife)

An in-memory data-structure store used for caching, sessions, rate limiting, queues, leaderboards, locks, and pub/sub. (Full Redis guide is next in the series.)

Databases

The durable heart of the system. Choosing the right database — and modeling data for access patterns — is the highest-stakes design decision.

FamilyExamplesBest for
Relational (SQL)Postgres, MySQLTransactions, relationships, strong consistency
DocumentMongoDBFlexible schema, nested data, fast iteration
Key-valueRedis, DynamoDBSimple lookups, caching, huge scale
Wide-columnCassandra, BigtableMassive write throughput, time-series
GraphNeo4jRelationship-heavy (social, fraud)
SearchElasticsearchFull-text search, log analytics
Polyglot persistence: real systems use several — Postgres for orders, Redis for cache/sessions, Elasticsearch for search, S3 for blobs, a queue for events. Choose per access pattern, not one DB for everything.

SQL vs NoSQL

SQL (relational)

  • Fixed schema, JOINs, ACID transactions
  • Strong consistency; great for money/orders
  • Vertical scale first; sharding is harder

NoSQL

  • Flexible schema; denormalized for access patterns
  • Horizontal scale built-in; often eventual consistency
  • Limited JOINs/transactions (varies by engine)

ACID vs BASE

ACID (SQL)BASE (many NoSQL)
Atomicity, Consistency, Isolation, DurabilityBasically Available, Soft state, Eventually consistent
Correctness first (banking)Availability/scale first (feeds, carts)
Interview trap: "NoSQL is faster/better" is wrong. Choose by access pattern & consistency needs: relational + transactional (payments) → SQL; huge scale, simple lookups, flexible data (feed, catalog) → NoSQL. Many systems use both.

CAP & PACELC

In a distributed data store, during a network partition you must choose between consistency and availability — you can't have both. That's the CAP theorem.

Consistency / \ / \ (during a PARTITION, pick one edge) Availability —— Partition tolerance CP: refuse/stall to stay consistent (banks; e.g. HBase, etcd) AP: answer with possibly-stale data (feeds; e.g. Cassandra, Dynamo) CA: only without partitions (a single node) — not real for distributed systems
PACELC extends it: if Partition → choose A or C; Else (normal operation) → choose Latency or Consistency. Real systems tune this per operation (e.g. Dynamo lets you pick consistency per read).
Common mistake: saying a system "gives up P". You can't give up partition tolerance in a distributed system (networks fail) — you choose C or A when a partition happens.

Replication

Keep copies of data on multiple nodes for availability (survive failures) and read scaling (serve reads from replicas).

Leader (primary) ──writes──▶ [ Leader ] ──replicate──▶ Follower(s) Reads: from leader (fresh) or followers (scale, but replication lag = stale)
TypeBehavior
Single-leaderAll writes to leader; followers replicate. Simple; leader is a bottleneck/SPOF (failover needed)
Multi-leaderWrites to several leaders (multi-region); conflict resolution needed
Leaderless (Dynamo)Write/read quorums (W+R>N); highly available
Sync vs asyncSync = no data loss, slower; async = fast, risk losing recent writes on failover
Replication lag causes "read-your-writes" bugs: a user updates their profile, then a read from a lagging replica shows the old value. Fix: read from the leader after a write, or route a user's reads to a consistent replica.

Sharding (Partitioning)

Split data across nodes so no single machine holds everything — the way to scale writes and storage horizontally.

StrategyHowTrade-off
RangeBy key range (A–M, N–Z)Easy ranges; hotspots if uneven
Hashhash(key) → shardEven spread; no range queries
Consistent hashingRing; adding a node moves few keysMinimizes reshuffle (used by Cassandra/Dynamo)
Directory / lookupA service maps key→shardFlexible; the lookup is a dependency
Hard parts: choosing a shard key (avoid hotspots — don't shard by country if one country dominates), cross-shard queries/joins (fan-out + merge), cross-shard transactions (avoid; use sagas), and rebalancing when you add nodes (consistent hashing helps).

✅ Key takeaways

  • Sharding scales writes/storage; replication scales reads/availability — usually combine both.
  • The shard key choice makes or breaks it — pick one with high cardinality and even distribution.

Indexing

An index is a sorted data structure (usually a B-Tree) that lets the DB find rows without scanning the whole table — the first fix for a slow query.

  • B-Tree — default; great for equality & range (WHERE age > 30, sorting).
  • Hash — O(1) equality only, no ranges.
  • Composite — multi-column; order matters (leftmost-prefix rule).
  • Covering index — includes all queried columns → answer from the index alone (fastest).
  • Inverted index — full-text search (Elasticsearch).
Trade-off: indexes speed reads but slow writes (every insert/update maintains them) and use space. Index the columns you filter/sort/join on; don't index everything. Use EXPLAIN to verify the query uses your index.

Load Balancing

Distribute traffic across many instances for scale + availability. The load balancer is also where health checks and failover live.

AlgorithmBehavior
Round robinRotate evenly
Least connectionsSend to the least-busy instance
WeightedBigger instances get more traffic
IP hash / stickySame client → same server (session affinity)
  • L4 (transport) — routes by IP/port, fast, protocol-agnostic.
  • L7 (application) — routes by URL/header/cookie; enables path-based routing, TLS termination.
  • Health checks remove unhealthy instances automatically; drain connections on deploy.
Statelessness enables it: if any instance can serve any request (session in Redis/DB, not in-memory), the LB can route freely and you can autoscale. Prefer stateless + a shared session store over sticky sessions.

Reverse Proxy

A server (Nginx, Envoy, HAProxy) that sits in front of your app servers and forwards client requests to them — often the same box that load-balances.

  • TLS termination — decrypt HTTPS once at the edge.
  • Caching & compression — serve cached/gzipped responses.
  • Routing & rewrites — path/host-based routing to services.
  • Security — hide backend topology, WAF, rate limiting, request buffering.
Forward vs reverse proxy: a forward proxy sits in front of clients (VPN, corporate egress). A reverse proxy sits in front of servers (Nginx before your API). Load balancers are a kind of reverse proxy.

API Gateway

A single entry point in front of many microservices that centralizes cross-cutting concerns so each service doesn't re-implement them.

Clients → [ API Gateway ] → user-svc │ → order-svc │ → payment-svc handles: auth · rate limiting · routing · request aggregation TLS · caching · logging/metrics · versioning
Gateway vs BFF: an API Gateway is a general edge for all clients. A Backend-for-Frontend is a gateway tailored to one client type (web vs mobile), aggregating/reshaping data for that UI. Big orgs often have both.
Don't put business logic in the gateway — keep it thin (routing + cross-cutting concerns). A fat gateway becomes a bottleneck and a deployment coupling point.

Rate Limiting

Protect services from abuse/overload by capping requests per client. A classic design question.

AlgorithmIdea
Token bucketTokens refill at a rate; each request spends one; allows bursts
Leaky bucketRequests drain at a fixed rate; smooths bursts
Fixed windowN per minute window; simple; boundary bursts
Sliding window log/counterAccurate rolling window; more memory
Distributed rate limit with Redis (fixed window)
# per user per minute
count = INCR rate:user:42:minute
if count == 1: EXPIRE rate:user:42:minute 60
if count > LIMIT: reject (429 Too Many Requests)
Distributed: counters must be shared across instances → keep them in Redis (atomic INCR). Return 429 + Retry-After; rate-limit at the gateway so services stay protected.

Authentication

Proving who a request is from. Two dominant models: server sessions and stateless JWT.

Sessions

  • Opaque session id in a cookie → server store (Redis)
  • Easy to revoke; server holds state
  • Store lookup per request; sticky/shared store at scale

JWT (stateless)

  • Signed token holds claims; server verifies signature
  • No lookup; scales horizontally
  • Hard to revoke early; keep short-lived + refresh token
Login → verify creds → issue access(15m JWT) + refresh(7d, rotated) Request → verify access token signature → allow Access expired → exchange refresh → new access; refresh reuse → revoke (theft detection)
OAuth2 / OIDC delegate auth to a provider (Google, Okta) — OAuth2 = authorization framework, OIDC adds identity (login). Use them for social/enterprise SSO instead of rolling your own.

Authorization

Deciding what an authenticated user may do. Distinct from authentication — always enforce it server-side at the data.

ModelIdeaUse
RBACRoles → permissions; users get rolesMost apps (admin/editor/viewer)
ABACRules over attributes (user, resource, context)Fine-grained (region, time, ownership)
ReBACRelationship graph (Google Zanzibar)Sharing/"who can access this doc"
Golden rule: authorization must be enforced on the server at the point the data is accessed — never trust the client, and don't rely only on hiding UI. Check ownership (does this order belong to this user?) on every request.

✅ Key takeaways

  • AuthN = who you are (sessions/JWT/OAuth); AuthZ = what you can do (RBAC/ABAC/ReBAC).
  • Enforce AuthZ server-side at the data; short-lived JWT + rotating refresh for scale.

Logging

Structured, centralized logs are how you debug production. First of the three observability pillars (logs, metrics, traces).

  • Structured JSON logs with levels (error/warn/info/debug) — machine-searchable.
  • Correlation / request ID on every log line → follow one request across services.
  • Centralize — ship to ELK/Loki/CloudWatch; never grep files on boxes.
  • Never log secrets/PII — redact tokens, passwords, card numbers.
Structured log line
{ "level":"error", "ts":"...", "reqId":"abc-123", "svc":"orders",
  "msg":"payment failed", "userId":42, "orderId":7 }

Monitoring & Metrics

Metrics are numeric time-series that tell you the system's health and drive alerts. Second observability pillar.

FrameworkTrack
RED (services)Rate, Errors, Duration
USE (resources)Utilization, Saturation, Errors
Golden signalsLatency, traffic, errors, saturation
  • Prometheus scrapes metrics; Grafana dashboards; Alertmanager pages on SLO breaches.
  • SLI/SLO/SLA: Indicator (measured), Objective (target, e.g. 99.9%), Agreement (contract). Alert on error budget burn, not every blip.
  • Alert on symptoms (high latency/error rate) users feel, not every CPU spike.
p99 > average: always chart latency percentiles. An average of 50ms can hide a p99 of 3s that's driving users away.

Distributed Tracing

Follow one request as it hops across many services — the only way to debug latency in a microservice system. Third observability pillar.

Trace (one request) = many Spans gateway ──▶ user-svc ──▶ auth-svc └─▶ order-svc ──▶ payment-svc ──▶ DB Each span: service, operation, start/duration, trace-id (propagated via headers)
OpenTelemetry is the standard: instrument once, export to Jaeger/Tempo/Datadog. A shared trace ID propagated in headers ties spans (and logs, via correlation IDs) together — you can see exactly which hop is slow.

Docker (Containers)

Package an app + its dependencies into a portable image that runs identically anywhere — the unit of modern deployment. (Full Docker guide is in the library.)

  • Image = immutable snapshot; container = a running instance.
  • Solves "works on my machine"; consistent dev → prod.
  • Lightweight (shares host kernel) vs VMs (full OS) → dense, fast.
  • Multi-stage builds → tiny production images; non-root user; scan for CVEs.
Why it matters for SD: containers make services identical and horizontally scalable — the substrate Kubernetes orchestrates.

Kubernetes (Orchestration)

Runs containers across a cluster with self-healing, scaling, rolling updates, and service discovery — the industry standard for operating services at scale.

ObjectRole
PodSmallest unit (1+ containers)
DeploymentDeclarative replicas + rolling updates/rollback
ServiceStable virtual IP + load balancing to pods
IngressHTTP routing into the cluster
ConfigMap / SecretConfig & secrets injection
HPAHorizontal Pod Autoscaler (scale on CPU/metrics)
Desired state (YAML) → Control plane → reconcile → actual state pod dies → recreated · traffic up → HPA adds pods · deploy → rolling update
Declarative & self-healing: you declare "I want 5 replicas"; K8s continuously reconciles reality to match. That control loop is the whole idea.

CI/CD

Automate build → test → deploy so changes ship safely and often.

commit → CI: lint · test · build image · scan · push → CD: deploy to staging → smoke tests → production deploy strategies: rolling · blue-green (instant switch) · canary (1%→100%)
  • CI — on every push: run tests, build a versioned artifact/image.
  • CD — promote artifacts through environments automatically with gates.
  • Blue-green — two prod environments, switch traffic instantly (easy rollback).
  • Canary — release to a small % first, watch metrics, then widen.
Decouple deploy from release with feature flags: ship code dark, turn it on gradually, kill it instantly if metrics dip — no redeploy.

Scalability

The full toolkit for handling growth — applied in roughly this order as load increases.

1 server ↓ add cache (Redis) + CDN (offload reads) ↓ add load balancer + more app servers (stateless, horizontal) ↓ add read replicas (scale reads) ↓ add queue + workers (async slow work) ↓ shard the database (scale writes/storage) ↓ split into services + regions (org + global scale)
Order matters: cache and CDN first (cheap, huge wins), then horizontal app scaling, then read replicas, then async, and only shard when a single DB truly can't keep up. Don't jump to sharding/microservices prematurely.

High Availability

Keep serving despite failures. HA = redundancy + automatic failover + no single point of failure.

  • Eliminate SPOFs — redundant instances, multi-AZ, replicated DB with failover.
  • Health checks + auto-restart/replace (K8s, load balancer draining).
  • Multi-AZ (survive a data-center failure); multi-region (survive a region failure).
  • Graceful degradation — shed non-critical features under stress rather than fail wholesale.
AvailabilityDowntime/year
99% ("two nines")~3.65 days
99.9%~8.8 hours
99.99%~52 minutes
99.999% ("five nines")~5 minutes
Availability is multiplicative: a request through 5 services each at 99.9% ≈ 99.5% overall. Redundancy at each hop and graceful degradation protect the end-to-end number.

Disaster Recovery

Plan for catastrophic loss (region outage, data corruption, ransomware). Defined by two targets:

TargetMeaning
RPO (Recovery Point Objective)How much data you can afford to lose (→ backup frequency)
RTO (Recovery Time Objective)How long recovery may take (→ standby strategy)
StrategyRTO/RPOCost
Backup & restoreHours (high)Low
Pilot lightCore running minimal, scale up on DRMedium

Untested backups don't exist. Regularly restore from backups and run DR drills — the worst time to discover a broken backup is during a real disaster.

Resilience Patterns

Distributed systems fail partially. These patterns stop one failure from cascading into an outage.

PatternWhat it does
TimeoutNever wait forever on a dependency
Retry + exponential backoff + jitterRecover from transient failures without stampeding
Circuit breakerStop calling a failing service; fail fast; probe to recover
BulkheadIsolate resource pools so one overloaded dependency can't sink everything
IdempotencySafe retries (idempotency keys) — no double charges
Fallback / graceful degradationServe cached/partial results when a dependency is down
Load shedding & backpressureReject/queue excess load to protect the core
Retry storms: naive retries during an outage multiply load and prevent recovery. Always add exponential backoff + jitter + a circuit breaker + a retry budget.

Consensus (Raft, Paxos, Quorums)

What: how a group of nodes agree on a single value (e.g. "who is the leader?", "what is the next log entry?") even when some nodes crash or messages are lost. Consensus is the beating heart of every replicated database, config store, and coordination service.

The problem it solves: with replication you have many copies of the data. If two nodes accept conflicting writes, the system diverges (split-brain). Consensus guarantees all healthy nodes apply the same operations in the same order, so replicas stay consistent.

Quorums — the math behind agreement

A quorum is a majority of nodes. With N nodes, a write quorum W and read quorum R guarantee strong consistency when W + R > N (read and write sets always overlap) and W > N/2 (no two writes commit without overlapping).

N = 5 nodes → majority = 3 Write needs 3 acks, Read needs 3 responses → W(3)+R(3)=6 > N(5) ✓ overlap guaranteed Tolerates failures: a cluster of N survives ⌊(N-1)/2⌋ node failures 3 nodes → survive 1 | 5 nodes → survive 2 | 7 nodes → survive 3 (That's why clusters use ODD counts — 4 nodes tolerate the same 1 failure as 3.)

Raft — understandable consensus (used by etcd, Consul, CockroachDB, TiKV)

Raft breaks consensus into three sub-problems: leader election, log replication, and safety.

Roles: Follower ──(election timeout)──▶ Candidate ──(wins majority vote)──▶ Leader Leader ──(higher term seen)──▶ Follower Normal operation (one leader per "term"): client → Leader appends entry to its log Leader → replicates entry to followers (AppendEntries RPC) once a MAJORITY have stored it → entry is COMMITTED → applied to state machine Leader tells followers the new commit index → they apply too Leader failure: followers stop hearing heartbeats → election timeout fires a follower becomes Candidate, increments term, requests votes node with the most up-to-date log wins → new Leader → continues the log
Raft conceptWhy it matters
TermLogical clock; every term has ≤1 leader; stale leaders step down when they see a higher term
Log matchingIf two logs agree on an entry's index+term, all prior entries are identical → simple, provable safety
Commit = majorityAn entry is durable once a quorum stores it; survives any minority failure
HeartbeatsLeader sends empty AppendEntries to assert authority and prevent needless elections
Paxos
  • The original (Lamport). Proven correct, powers Google Chubby & Spanner.
  • Notoriously hard to understand & implement correctly.
  • Multi-Paxos adds a stable leader for efficiency.
Raft
  • Designed for understandability; same guarantees as Multi-Paxos.
  • Strong leader + explicit terms make it easier to reason about.
  • The modern default (etcd, Consul, CockroachDB).
Where you meet consensus in real life: Kubernetes stores all cluster state in etcd (Raft). Kafka's controller quorum (KRaft) uses Raft. ZooKeeper (ZAB, a Paxos-like protocol) coordinates HBase/older Kafka. Any time a system needs a single source of truth for leadership or config, a consensus protocol is underneath.
Cost: consensus requires a network round-trip to a majority on every write → higher latency. Keep consensus groups small (3–5 nodes) and only put metadata (leadership, config, small critical state) through them — not your bulk data throughput.

Consistent Hashing

What: a hashing scheme that maps both keys and servers onto the same ring, so adding or removing a server moves only a small fraction of keys instead of remapping everything.

The problem it solves: naive sharding uses server = hash(key) % N. The moment N changes (a node joins or dies), almost every key maps to a different server → a cache-wide miss storm and a massive data reshuffle. Consistent hashing makes that cost proportional to 1/N.

Hash ring (0 … 2^32-1), servers placed at hash(serverID): ┌───────── A ─────────┐ (keys go clockwise to ) (the next server on ring ) D ◀ ▶ B \ / └────────── C ──────────┘ Lookup: key → hash(key) → walk clockwise → first server owns it. Add server E between A and B → only keys in (A,E] move from B to E. Remove C → only C's keys move to the next server (D). Everything else stays put.

Virtual nodes (vnodes) — fixing lopsided rings

With few servers, random placement creates uneven load. The fix: hash each physical server to many points on the ring (e.g. 100–200 vnodes each). This smooths distribution and lets more-powerful nodes hold more vnodes (weighting).

AspectModulo hashingConsistent hashing
Keys moved when N changes≈ all (N-1)/N≈ 1/N
Load balanceEvenEven with vnodes
Used bySimple fixed clustersDynamoDB, Cassandra, Riak, Redis Cluster (slot variant), CDNs, memcached clients
Redis Cluster nuance: Redis uses 16384 fixed hash slots (a bounded, explicit variant of the same idea): slot = CRC16(key) mod 16384. Slots are assigned to nodes; resharding moves whole slots. Same goal — minimal, predictable data movement — with simpler bookkeeping.

Distributed Transactions (2PC, Saga, Outbox, Idempotency)

The problem: a single business action (place order → charge payment → reserve stock) spans multiple services/databases. There is no shared BEGIN/COMMIT. How do you keep them consistent when any step can fail?

Two-Phase Commit (2PC) — strong but fragile

Coordinator asks all participants: PHASE 1 "PREPARE" (can you commit?) all reply YES → PHASE 2 "COMMIT" | any replies NO → "ABORT" (rollback all) Problem: if the coordinator crashes after PREPARE, participants are BLOCKED holding locks until it recovers. Synchronous, low throughput, single point of failure. Used inside a DB / XA transactions — rarely across microservices at scale.

Saga — the microservices answer

A saga is a sequence of local transactions; each step publishes an event that triggers the next. If a step fails, previously-completed steps are undone with compensating transactions (semantic rollback — e.g. "refund payment", not a DB rollback).

Choreography
  • Services react to each other's events — no central brain.
  • Simple for a few steps; decoupled.
  • Hard to follow & debug as steps grow (event spaghetti).
Orchestration
  • A central orchestrator tells each service what to do next.
  • Explicit, easy to visualize & monitor the flow.
  • Orchestrator becomes a critical component to keep available.
Order Saga (orchestrated): create order(pending) → charge payment → reserve inventory → confirm order If inventory fails ▶ compensate: refund payment → cancel order Sagas give ATOMICITY-of-outcome via compensation, but only EVENTUAL consistency (there are brief windows where payment succeeded but order not yet confirmed).

The dual-write problem & the Outbox pattern

You must "update my DB and publish an event". Doing both directly is unsafe — a crash between them loses the event or double-sends it. The Transactional Outbox writes the event into an outbox table in the same DB transaction as the business change. A separate relay (often CDC via Debezium) reads the outbox and publishes to the broker — guaranteeing the event is sent iff the data was committed.

One local TX: UPDATE orders ... + INSERT INTO outbox(event) ... ✓ atomic Relay/CDC: tail outbox / DB log → publish to Kafka → mark sent Result: no lost events, no phantom events. At-least-once delivery downstream.

Idempotency — the glue that makes retries safe

Because async delivery is at-least-once, consumers WILL sometimes see a message twice. Idempotency makes processing the same message twice have the same effect as once.

TechniqueHow
Idempotency keyClient sends a unique key per request; server stores it and returns the prior result on replay (payments APIs do this)
Dedup table / processed-IDsRecord each handled message ID; skip if already seen
Natural idempotencyDesign ops as "set state to X" (idempotent) rather than "increment" (not)
Upsert / conditional writesUse unique constraints or compare-and-set so duplicates collapse
Exactly-once is a lie (mostly): across a network you get at-most-once or at-least-once. "Exactly-once processing" is really at-least-once delivery + idempotent consumers (or transactional dedup, as in Kafka's EOS). Design for duplicates — don't assume they can't happen.

Event-Driven Architecture, CQRS & Event Sourcing

What: instead of services calling each other synchronously, they emit events ("OrderPlaced", "PaymentCaptured") to a broker; interested services react. This decouples producers from consumers in time, scale, and deployment.

Request/response (sync)
  • Caller waits; tight coupling.
  • Simple, immediate consistency.
  • Cascading failure: a slow dependency slows the caller.
Event-driven (async)
  • Fire-and-forget; loose coupling.
  • Elastic — consumers scale independently, absorb spikes via the log.
  • Eventual consistency; harder to trace end-to-end.

CQRS — Command Query Responsibility Segregation

Split the model that writes (commands) from the model that reads (queries). Writes go to a normalized store optimized for consistency; a projection builds denormalized read models (often in a fast store like Redis/Elasticsearch) optimized for the query shapes your UI needs.

Command side: API → validate → write to store → emit event │ Read side: event → projector → materialized read view(s) (Redis/ES/SQL view) Queries hit the pre-shaped read model → blazing fast, independently scalable. Trade-off: read model is EVENTUALLY consistent with the write model.

Event Sourcing — the log IS the source of truth

Instead of storing current state, store the full ordered sequence of events. Current state is derived by replaying events. Gives you a perfect audit log, time-travel, and the ability to build new projections from history.

BenefitCost / caution
Complete audit trail & temporal queriesReplays get slow → use snapshots
Rebuild any read model from scratchEvent schema evolution is hard (versioning/upcasting)
Natural fit with CQRS & KafkaHigher complexity — don't use it everywhere
Pragmatic advice: most systems only need plain event-driven messaging + maybe CQRS for a few hot read paths. Reserve full event sourcing for domains where the history itself is the product (ledgers, banking, order lifecycles, audit-heavy systems).

Database Internals (WAL, B-Tree vs LSM, MVCC, Pooling)

Knowing how a database stores and protects data lets you choose the right engine and explain performance in interviews.

Write-Ahead Log (WAL) — durability without slow random writes

Before changing data pages, the DB appends the change to a sequential WAL and fsyncs it. A sequential append is fast; the actual pages are updated later (asynchronously). On crash, the WAL is replayed to recover committed changes. This is the "D" in ACID and the basis of replication (ship the log to replicas).

B-Tree vs LSM-Tree — the two storage-engine families

B-Tree (read-optimized)
  • Balanced tree of pages, updated in place.
  • Great random reads; predictable latency.
  • Writes touch pages randomly → more write amplification.
  • Postgres, MySQL/InnoDB, most RDBMS.
LSM-Tree (write-optimized)
  • Buffer writes in memory (memtable) → flush sorted files (SSTables) → compact in background.
  • Excellent write throughput; sequential I/O.
  • Reads may check several levels → bloom filters help.
  • Cassandra, RocksDB, LevelDB, ScyllaDB, HBase.
LSM write path: write → memtable (RAM) + WAL memtable full → flush → immutable SSTable (disk, sorted) background COMPACTION merges SSTables, drops tombstones LSM read path: memtable → bloom filter → SSTable levels (newest→oldest)

MVCC — readers don't block writers

Multi-Version Concurrency Control: each write creates a new version of a row tagged with a transaction timestamp. Readers see a consistent snapshot as of their start; they never block writers and vice-versa. Old versions are cleaned up later (Postgres VACUUM). This is how "repeatable read"/"snapshot isolation" is implemented without heavy locking.

Connection pooling — don't pay TCP+auth per query

Opening a DB connection is expensive (TCP handshake, TLS, auth, backend process). A pool keeps a set of warm connections and hands them out. Size it near cores × 2-ish (not thousands) — too many connections thrash the DB. For serverless/high-fanout, front the DB with a pooler (PgBouncer, RDS Proxy).

Pool exhaustion is a classic outage: a slow query holds connections, the pool drains, new requests queue and time out. Fix with query timeouts, right-sized pools, circuit breakers, and killing long-running queries.

Service Mesh & Backpressure

Service mesh: a dedicated infrastructure layer that handles service-to-service networking — retries, mTLS, timeouts, load balancing, traffic shifting, and telemetry — without changing app code, by injecting a sidecar proxy (e.g. Envoy) next to every service.

Without mesh: each service reimplements retries/TLS/metrics/tracing in code (per language!) With mesh: ┌── Pod ──────────────┐ ┌── Pod ──────────────┐ │ app ⇄ [Envoy sidecar]│ ⇄ mTLS ⇄ │[Envoy sidecar] ⇄ app │ └─────────┬───────────┘ └───────────┬─────────┘ DATA PLANE (sidecars carry all traffic) CONTROL PLANE (Istio/Linkerd) configures every sidecar centrally Gives: mTLS everywhere, uniform retries/timeouts, canary/blue-green routing, circuit breaking, and golden metrics/traces — language-agnostic.
ConcernMesh handles it
SecurityAutomatic mutual TLS + service identity
TrafficCanary, blue-green, traffic mirroring, weighted routing
ResilienceRetries, timeouts, circuit breaking, outlier ejection
ObservabilityConsistent metrics, logs, distributed traces for every call
Not free: a sidecar per pod adds latency, memory, and operational complexity. Adopt a mesh when you have many services in multiple languages needing uniform security/observability — not for a handful of services.

Backpressure & flow control

Backpressure is a consumer signalling "slow down, I'm overwhelmed" so a fast producer can't drown it. Without it, queues grow unbounded → memory blows up → the whole pipeline collapses.

MechanismHow it applies backpressure
Bounded queuesFull queue blocks/rejects producers instead of growing forever
Pull-based consumersConsumer requests N items when ready (Kafka, Reactive Streams)
TCP flow controlReceive window naturally throttles a fast sender
Load sheddingDrop/deprioritize excess load (429s) to protect the core
Rate limiting & concurrency capsCap in-flight work so downstreams aren't overrun
Rule of thumb: every queue must be bounded and every unbounded buffer is a future out-of-memory outage. Design the whole pipeline so the slowest stage can push back on the fastest.

Case Studies

Apply the toolkit. For each: requirements → estimation → data model → architecture → bottlenecks.

🔗 Design a URL Shortener (TinyURL / bit.ly)

Requirements: shorten URL, redirect fast, analytics; read-heavy (100:1) Key gen: base62(counter) or hash(long URL) → 7 chars = 62^7 ≈ 3.5T Data: KV store {short → long}; write-once, read-many Arch: API → cache(Redis) → DB(KV, e.g. Dynamo); redirect = cache hit (301/302) Scale: heavy caching + CDN; sharded KV; async analytics via queue Bottleneck: redirect latency → cache everything; ID collisions → counter/uniqueness

🚦 Design a Distributed Rate Limiter

Requirements: N req/user/window across many gateway instances Algo: token bucket / sliding window State: shared counters in Redis (atomic INCR + EXPIRE, or Lua for sliding) Arch: gateway → Redis check → allow / 429 + Retry-After Scale: Redis Cluster; local pre-check + async sync to reduce Redis load

💬 Design a Chat System (WhatsApp)

Requirements: 1:1 + group, delivery/read receipts, presence, offline delivery Transport: WebSocket (persistent) via connection gateway; ack for delivery Data: messages in wide-column (Cassandra) partitioned by conversation Offline: queue undelivered → push on reconnect; fan-out for groups Scale: stateless WS gateways + a session registry (which server holds a user)

🔔 Design a Notification System

Producer → Kafka(topic) → workers → channels (push/email/SMS) via providers Features: templating, user prefs, dedupe, retries+DLQ, rate limit per user Scale: fan-out via queue; idempotency keys; provider failover

📰 Design a News Feed (Twitter/Instagram)

Write (post): store post → fan-out fan-out-on-write (push): precompute followers' feeds (fast reads, heavy for celebs) fan-out-on-read (pull): build feed at read time (cheap writes, slower reads) hybrid: push for most, pull for celebrities (the real-world answer) Data: posts (KV/Cassandra), feed cache (Redis), media (S3+CDN); rank + paginate (cursor)
How to shine: clarify scale (estimation) → propose components → name the key trade-off (e.g. fan-out on write vs read) → go deep where probed → mention bottlenecks & how you'd monitor them.

Interview Questions

🟢 Fundamentals

Vertical vs horizontal scaling?

Vertical = a bigger machine (simple, but has a ceiling and is a SPOF). Horizontal = more machines behind a load balancer (near-limitless, fault-tolerant) — requires stateless services and data partitioning.

What makes a service horizontally scalable?

Statelessness — no in-memory session/state. Put shared state in Redis/DB so any instance can serve any request, letting a load balancer route freely and autoscalers add instances.

Explain the CAP theorem.

During a network partition a distributed store must choose Consistency (reject/stall to stay correct — CP) or Availability (answer with possibly-stale data — AP). You can't sacrifice partition tolerance; PACELC adds the latency-vs-consistency choice during normal operation.

🟡 Data

SQL vs NoSQL — how do you choose?

By access pattern and consistency needs. Relational + transactional (payments, orders) → SQL/ACID. Huge scale, simple lookups, flexible/denormalized data (feeds, catalogs) → NoSQL/BASE. Many systems use both (polyglot persistence).

Replication vs sharding?

Replication = copies of the same data (availability + read scaling; watch replication lag). Sharding = split different data across nodes (write/storage scaling; needs a good shard key). Usually combine: shard, and replicate each shard.

How do you pick a shard key?

High cardinality and even distribution to avoid hotspots; aligned with common query access so you don't fan out across shards. Consistent hashing minimizes rebalancing when adding nodes. Avoid low-cardinality keys (e.g. country) that concentrate load.

How does caching go wrong?

Stale data (design invalidation), cache stampede when a hot key expires (locks/singleflight, staggered TTLs), hot keys overwhelming a node (replicate/shard the key), and thundering herd on cold start (warm the cache).

🔵 Architecture

How do you handle a transaction across microservices?

Use a Saga: a chain of local transactions coordinated by events (choreography) or an orchestrator, with compensating transactions to undo on failure. Publish events atomically with the DB write via the Outbox pattern; make handlers idempotent.

Sync vs async communication — when each?

Sync (REST/gRPC) when the caller needs the result immediately. Async (queue/events) for slow, optional, or fan-out work (email, thumbnails, search indexing) — it keeps requests fast, decouples services, and absorbs spikes at the cost of eventual consistency.

Monolith or microservices for a new product?

Start with a modular monolith — simpler to build/deploy/debug. Extract microservices only when a concrete scaling or team-ownership need appears. Premature microservices add distributed-systems complexity you don't need yet.

🟣 Reliability & Production

How do you prevent cascading failures?

Timeouts on every dependency, retries with exponential backoff + jitter, a circuit breaker to fail fast when a service is down, bulkheads to isolate resource pools, load shedding under overload, and graceful degradation (serve cached/partial data).

How do you make a system observable?

The three pillars: structured logs with correlation IDs, metrics (RED/USE, alert on SLOs and p99), and distributed tracing (OpenTelemetry) to follow a request across services. Alert on user-facing symptoms, not every resource blip.

What are RPO and RTO?

RPO = how much data you can lose (drives backup frequency); RTO = how long recovery may take (drives standby strategy: backup/restore → pilot light → warm standby → active-active). Test restores regularly — untested backups don't count.

Design a rate limiter for a distributed API.

Token bucket or sliding window with counters in Redis (atomic INCR + EXPIRE, or a Lua script for accuracy) so all gateway instances share state. Return 429 + Retry-After; enforce at the gateway; shard/replicate Redis and consider a local pre-check to cut Redis load.
